An `ai-agent` is stateless by default: each invocation starts a fresh
conversation. Set `memoryThreadId` and the agent loads the thread's prior
transcript before its run and saves the accumulated transcript after, so a
conversation persists across invocations.

![A deployment's object store holding both memory layers: per-thread agent-memory keys and a durable slack:user-facts key](/screenshots/platform-object-browser.png)

## Per-thread conversation memory

```yaml
service:
  name: ai-agent-memory

env:
  - name: ANTHROPIC_API_KEY
    required: true

connectors:
  - name: claude
    type: llm-anthropic
    settings:
      apiKey: ${ANTHROPIC_API_KEY}

flows:
  - name: chat
    process:
      - type: ai-agent
        name: assistant
        connector: claude
        # Per-thread memory: load/save this thread's transcript around the run.
        memoryThreadId: body.threadId
        contextMaxTokens: 8000
        memoryCompaction: summarize
        prompt: >
          You are a helpful assistant in an ongoing conversation. Use the prior
          turns for context and answer the user's latest message. Respond with a
          JSON object {"reply": "..."}.
        tools:
          - name: remember_note
            description: Save a short note to scratch state for later in this task.
            inputSchema: |
              {"type":"object","required":["note"],"properties":{"note":{"type":"string"}}}
            process:
              - type: set-variable
                settings:
                  name: note
                  value: body.note
```

Invoke it twice on the same thread and the second turn remembers the first:

```bash
octo invoke --config samples/ai-agent-memory.yaml --flow chat \
  --data '{"threadId":"user-42","message":"My name is Sam."}'
octo invoke --config samples/ai-agent-memory.yaml --flow chat \
  --data '{"threadId":"user-42","message":"What is my name?"}'
```

### Choosing a thread id

`memoryThreadId` is a CEL expression over the message, so the thread
granularity is yours: per user (`body.userId`), per channel, or per
conversation. The production Slack agent computes it upstream with a
transform — `"slack:dm:<channel>"` for direct messages,
`"slack:<channel>:<threadTs>"` for channel threads — so every Slack thread
gets its own memory.

Transcripts are stored in the runtime KV store under a dedicated
`agent-memory/` prefix in the user namespace, so they never collide with
`object-read`/`object-write` keys.

### A thread id is the whole identity

The thread is what a transcript is keyed by, and nothing else is. Two `ai-agent`
blocks that resolve the same id therefore share one conversation: each loads what
the other wrote, answers with it in context, and saves over it.

That is easiest to write by accident with a **nested agent** — an `ai-agent`
standing in another agent's tool slot. A tool branch runs on the agent's own
message, so the nested one sees the caller's variables, and `vars.threadId` is the
obvious expression in both blocks.

The runtime mints a scope for every tool branch, which is the answer:

```yaml
# A conversation of its own, kept out of the store that is backed up.
memoryThreadId: vars.toolScope
memoryVolatile: true
```

`vars.toolScope` is stable for as long as the caller's conversation and distinct
per tool, so a specialist called three times in one conversation is the same
specialist each time, and two specialists never share. Nothing in the calling
agent configures it: the runtime knows which call it is making and what
conversation it is in, so it composes the two — see
[what a tool branch is told](/reference/blocks/ai#what-a-tool-branch-is-told).

Or leave `memoryThreadId` out. A specialist handed a complete brief that answers
once has nothing to remember, and a stateless agent claims nothing — which is what
Dr. Octo's two specialists do.

<Callout type="info">
`toolScope` is **derived** — from the conversation, the calling block and the tool
— so it cannot be lost the way a stored id can. The cost of deriving it partly
from where the block sits is that it moves when the block does: rename the agent,
or move it into another branch, and its tools start again somewhere new. That is
the right trade for scaffolding and the wrong one for history, which is why the
recipe pairs it with `memoryVolatile` and why nothing durable is keyed this way.

If you want one id shared by *several* tools in a conversation — which derivation
cannot express, since it is distinct per tool — mint one and memoize it:

```yaml
- type: set-variable                 # cache-scope caches the body, so stash the args
  settings: { name: args, value: body }
- type: cache-scope
  key: vars.threadKey
  ttl: "0"                           # the default 60s would re-mint mid-conversation
  body:
    process:
      - type: set-payload
        settings: { value: '{"id": uuid()}' }
- type: set-variable
  settings: { name: shared, value: body.id }
- type: set-payload
  settings: { value: vars.args }     # hand the tool its arguments back
```

That id is stored rather than derived, so treat eviction as part of the design: a
TTL, an `invalidate-cache` on the same key, or a wiped store mints a new one and
whatever was keyed on it starts fresh.
</Callout>

### Volatile memory

`memoryVolatile: true` puts an agent's transcripts in the volatile KV tier — Redis
in a cluster, process memory standalone — instead of the persistent one.

Use it for a conversation whose loss costs nothing. A specialist's working
transcript is scaffolding, and one row per tool per conversation would otherwise
accumulate in the store the platform backs up and reports on; the volatile tier is
bounded and evicts under LRU, so scaffolding cleans up after itself.

Never use it for a conversation somebody will ask to see again: the tier makes no
durability promise and may drop a value on a restart. `clear-agent-memory` clears
both tiers, so a "forget this" reaches either.

The runtime does not invent a namespace for you here. It could key a transcript by
the block's address as well as the thread — and then renaming that block, or moving
it into an `if`, would silently lose every conversation it had, which is a worse
failure than the one it prevents. What it does instead is **say so**: when a run
claims a conversation another live run in the same process is already working, it
logs a warning naming both blocks, the thread, and what to do about it.

<Callout type="warn">
A transcript also lives in the **deployment's** KV scope, so undeploying an
integration erases the conversations it held — a reinstall starts everyone from
nothing. A roll-out keeps them: it is the same deployment. See
[#362](https://github.com/juancavallotti/octo/issues/362).
</Callout>

### Token budget and compaction

`contextMaxTokens` (default `16000`) caps the agent's **whole prompt** —
system instructions, tool schemas and conversation together — not the stored
transcript alone. The figure comes from the provider: every turn reports how
many tokens it actually read, so the budget is measured rather than guessed,
and it is directly comparable to the model's context window.

The runtime still has no tokenizer, and it does not need one. The measured
total says exactly how big the prompt is; a chars/4 estimate is used only to
apportion that total across messages when deciding where to cut, and its
ratio is fitted against the provider's own numbers as the run goes. A
provider that reports no usage falls back to the estimate alone.

The budget applies **with or without memory**: an agent can talk itself past
the model's window inside a single run, over enough tool calls. When the
prompt would exceed the budget, the transcript is compacted with the
`memoryCompaction` strategy — before the turn that would have overflowed, and
again before saving:

- **`prune`** (default) — drop the oldest turns until the transcript fits.
  Cheap and deterministic; old context is simply gone.
- **`summarize`** — keep the most recent turns that fit half the budget and
  ask the same LLM connector to fold the older turns into a single summary
  message, preserving facts and decisions. Falls back to pruning if the
  summary cannot be produced.

### Watching it happen

Compaction is bracketed by `compaction_start` and `compaction_end` events, the
way a model turn is. Both carry `strategy` and the context gauge
(`contextTokens`, `contextMaxTokens`); the end event adds `after` and
`dropped`. It is bracketed rather than reported once because the `summarize`
strategy makes a model call, so compaction can take seconds — a progress UI
with only an after-the-fact event would show a stall it cannot explain.

The gauge also rides on every `turn_end`, so a UI can show the context filling
rather than only the moment it overflowed. There the reading is exact: the
prompt the provider reported reading, plus the reply it produced.

Compaction also writes an **`agent.compaction` trace record**, carrying the
same figures. It has its own kind because it is not a model turn: pruning calls
no model and costs nothing, so it would otherwise leave no trace at all — and
when an agent has forgotten something, when it forgot is the first thing anyone
needs. Summarizing *does* call a model, and that call is recorded separately as
an `llm.turn` marked `purpose: memory-compaction`, so the cost lands where cost
is read and the compaction record stays about the decision.

<Callout type="info">
Saving memory is best-effort: a failed save is logged and does not fail the
flow. Memory is also persisted when the agent takes its guardrail path, so a
refused turn still stays in the conversation.
</Callout>

<Callout type="warn">
A budget too small to hold even one exchange cannot be satisfied — compaction
will not discard the conversation to meet it. It keeps the most recent
exchange, logs that the result does not fit, and leaves the fix to you.
</Callout>

### Clearing a thread

The `clear-agent-memory` leaf block wipes a thread's stored transcript. It
is idempotent — clearing a missing thread is not an error — and passes the
message through unchanged:

```yaml
  - name: forget
    process:
      - type: clear-agent-memory
        name: wipe-thread
        settings:
          threadId: body.threadId
      - type: set-payload
        settings:
          value: '{"cleared": true}'
```

## The second layer: durable facts

Conversation memory is a transcript with a budget — it fades as it is
compacted, and it is scoped to one thread. For facts that should survive
across conversations ("prefers Celsius", "leads the billing team"), the
production Slack agent adds a second layer the agent manages itself: two
tools backed by the object store, plus a skill teaching the model when to
use them.

The tools are sourceless flows invoked via `flow-ref`. `remember_user_fact`
appends one bullet to a per-user document; `retrieve_user_facts` reads it
back:

```yaml
  - name: remember-user-fact
    process:
      - type: object-read
        settings:
          key: vars.userFactsKey     # e.g. "slack:user-facts:U123"
          as: existingUserFacts
          default: '{"facts": ""}'
      - type: set-variable
        settings:
          name: updatedUserFacts
          value: string(vars.existingUserFacts.facts) + "- " + string(body.fact) + "\n"
      - type: object-write
        settings:
          key: vars.userFactsKey
          value: '{"facts": vars.updatedUserFacts}'
      - type: set-payload
        settings:
          value: '{"stored": true, "fact": body.fact}'
```

A `user_memory` skill tells the agent the policy — recall near the start of
a turn, store only stable, self-contained facts, never announce it:

> Store: when the user shares a stable preference, personal fact, working
> style, recurring context, or anything that would help future replies, call
> `remember_user_fact` with one short standalone fact. Keep each fact
> self-contained ("Prefers Celsius", "Works in the Berlin office") rather
> than a snippet of the chat.

The two layers complement each other: the built-in transcript gives the
agent short-term conversational context for free, while the fact store gives
it long-term, cross-conversation knowledge under explicit rules you author.
See the [Slack agent capstone](/ai/slack-agent) for the full walkthrough,
and [Skills and Tools](/ai/agent-skills-and-tools) for how skills and
flow-backed tools work.
