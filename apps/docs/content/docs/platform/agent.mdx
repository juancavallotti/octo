import { Callout } from 'fumadocs-ui/components/callout';

Ask **Dr. Octo** about this installation and he answers: he reads and explains your integrations, writes and fixes flow definitions, and investigates deployments that will not start. Install him from **Admin → Platform agent** at `/platform/admin/agent`.

Understand one thing first and the rest of this page follows from it: **Dr. Octo is an ordinary integration.** He is not a service, a sidecar, or a bundled image — he is a `config.yaml` with an [`ai-agent`](/reference/blocks/ai) block in it, installed as a real integration and deployed through the same path you deploy anything.

So treat him as one:

- Look for his logs, traces, scaling and [version history](/platform/snapshots) exactly where you look for any deployment's. None of it was written for the agent, and all of it works on him.
- **Open him in the editor and change him.** Follow the link on the status card, then edit the prompt, add a tool, remove one, rewrite a skill.

## Before you install

Installing needs three things. Check them here, or just open the page — it tells you which one is missing instead of failing:

| Requirement | Why | If it is missing |
| --- | --- | --- |
| Cluster access | He is deployed like any integration | **Install** is disabled; this orchestrator cannot deploy anything |
| `kv.encryptionKey` | His provider key is read back out of storage to bind onto the deployment | **Install** is disabled — see [Admin settings](/platform/admin-settings) |
| A stored LLM key | There is no model for him to reason with | **Install** is disabled, with a link to the LLM provider section on the same page |

Expect the status page never to fail for a reason you could act on: no cluster, no encryption key and no provider key each arrive as an explanation on the page rather than an error.

## Install him

Press **Install**. That creates the integration, writes his skills as [resources](/platform/resources-and-secrets), publishes a version tag derived from the bundle this orchestrator ships, writes the provider key as a cluster secret, and deploys him with one replica and **no external route**.

He is deployed with both [platform access grants](/platform/deployments#platform-access) — he asks for them the way any integration does, rather than through a private path. The observability grant is what puts `LOGS_URL` in his pod and lets him read stored logs and traces; without it he still installs and works, and simply says he was not granted that access when asked about history.

<Callout>
Granting him observability hands a chat-panel user nothing they could not already read. [Traces](/platform/traces) and [Logs](/platform/logs) are readable by any signed-in user, while the chat panel additionally requires the write roles — so anyone who can ask him is already entitled to open those views directly, and to far more besides. Untick the grant and roll out if you want him without it anyway; the reason to weigh is prompt injection, below, not the reader's own entitlement.
</Callout>

Press it twice if you are unsure — it is idempotent. An existing integration is reused and an existing tag is not recreated, so you never get a second agent, and retrying after a failed deploy picks up where it stopped.

Note that he is deployed **internal-only**. Nothing outside the cluster reaches him directly; the platform proxies to the in-cluster address shown on the status card.

<Callout type="warn">
Dr. Octo has full read **and write** access to the orchestrator API, deploying included. The chat panel is therefore gated by `AUTH_WRITE_ROLES`, the same roles every other cluster-wide write requires — and **that variable defaults to empty, which means any signed-in user**. Set it before you install him on a shared installation. To narrow what he may do regardless of who asks, see [Restrict what he can do](#restrict-what-he-can-do).
</Callout>

## Talk to him

Once he is running, look for the round button in the bottom-right corner of any signed-in page. It appears only when he is deployed **and you hold the write roles** — he can write, so the drawer requires what any other write requires. If you do not see it, check both.

It opens as a full-height drawer down the right-hand side, over the page rather than pushing it — so when he takes you somewhere you can watch the page behind it change.

Type a question and the answer streams back a word at a time. Expect five things in the drawer that a plain chat box does not have:

- **Markdown.** He answers in it, so a flow definition arrives in a code block you can copy, and a comparison arrives as a table.
- **His working, in order.** What he thought, what he called, what he thought about the answer, and then his reply — laid out in the sequence it happened. A run that looks something up and then changes its mind is legible as exactly that. Reasoning follows itself while it is the latest thing he has done, and collapses to a one-line summary the moment anything comes after it; click that line to read it again.
- **A running commentary.** Above the message box, a line saying what he is doing right now: thinking, running a named tool, reading what came back, shortening the conversation. It stays put while you scroll.
- **A context gauge.** Once a conversation is more than half way through his budget, the header shows how full it is. It is the warning that he is about to start forgetting the beginning.
- **Navigation.** When the answer to your question is a page, he takes you there and says why. He can only reach pages inside the platform — the drawer refuses any other destination, whatever his definition has been changed to say.

Scrolling up stops the view following the answer, so you can re-read something while he is still writing; a **Latest** button appears while it is off, and returning to the bottom turns it back on.

Press **Stop** to end a run in progress, or close the panel. Closing aborts the request, which ends the run — the runtime sees the connection go and stops rather than leaving a model generating for nobody. **Stop** does something slightly different and stronger: it sends a stop for the *conversation*, so it ends the run wherever it is running, including on a replica this browser never spoke to.

You can also type while he is working. A message sent mid-answer is handed to the run already in flight rather than starting a second one, so he takes it into account on his next turn instead of answering you twice on two streams.

Such a message is sent as the question alone — the run it joins already knows what page you are on and where it may take you, so a follow-up does not repeat any of it. It is shown as unread until he picks it up. Nothing comes back on the request that carries it — the answer is going to the stream you already have open — so a bubble that looked sent would look identical whether he folded it in or dropped it. It waits, and when the run says it read it — which can be a whole model call later — it moves into the conversation at that point and is marked **Read, and taken into account**. Whatever he does about it, the reasoning and the tool calls, then appears underneath it rather than being added to the answer it interrupted. If the run ends first, or he runs out of steps before reaching it, it says so and tells you to ask again: that is the one case where something you sent goes nowhere, and it is not allowed to be silent.

A message sent from somewhere else — a second tab, or this window before you reloaded it — appears the same way: it is written into the conversation where he read it, so a reply that changes direction has something visible to change direction about.

Sending from a window that cannot tell a run is already going is a different matter. It still reaches that run, because the runtime knows even when the browser does not, but the answer goes to whoever is reading it rather than to you. The panel says so where the reply would have been, rather than leaving a blank turn.

Press **New conversation** to start fresh — that drops the thread, and with it what he remembers of it. The conversation itself is kept, and you can come back to it: past conversations are listed by name in the panel.

He knows which page you are on, so ask about "this integration" or "this deployment" and expect him to know what you mean.

<Callout>
Conversations are scoped to you. The panel sends a thread id, but he keys his memory on the signed-in user *and* that thread, and the identity comes from your session on the server rather than from the browser — so a thread id belonging to someone else names a conversation that does not exist.
</Callout>

### Coming back to one

Every exchange is recorded as it happened, under a name he writes for the conversation on its first message. The history button in the drawer's header lists them; opening one replays it and continues the thread, so the next thing you say lands in the same conversation.

What comes back is what was **said** — your messages and his answers. The reasoning and the tool calls belonged to the run and went with it.

That record is deliberately **not** his memory. Memory is compacted — a long conversation has its early turns replaced by a summary of them, which is what keeps the model's context affordable — so it is the working set rather than the conversation you had. Only one of the two can be read back to you, and it is this one.

The record is written from a wire-tap: the exchange goes onto an internal queue and the answer returns, so naming a conversation (which is a small model call, once per conversation) never delays a reply. Both the list and the transcripts are keyed on the signed-in user, exactly as memory is.

Two limits worth knowing:

- **A message you send mid-answer is not in the replay.** It reaches the run — that is what steering is — and he takes it into account, but the record is written once per completed run and holds the question that started it. The answer reflects your follow-up; the transcript does not show you making it.
- **Naming can fail, and the record does not.** A provider having a bad minute leaves the conversation named after its first question instead. A worse name, not a worse record.

## Update him

His definition ships inside the orchestrator binary, so upgrading the platform can bring a newer one. When it does, the page reports **Update available**. Press **Roll out update** to publish the new bundle as a version and roll his deployment onto it.

Nothing happens silently: a newer bundle waits for you, and installing never happens twice.

## Put him back the way he shipped

There is one button on a deployed agent, and it always does the same thing — republish the definition this orchestrator ships and replace his pods with it. Only its name changes, to say which of the three reasons you are pressing it for:

| It reads | When |
| --- | --- |
| **Roll out update** | A newer bundle ships with this orchestrator |
| **Redeploy** | The deployment is in a failed state |
| **Reinstall from stock** | Neither — he is current and running |

Reach for the last one after editing him into a state you would rather undo, or when he is running something you no longer trust. Before, there was no way back: the button only appeared when the shipped digest had moved or the deployment had failed, so an agent that was current, running and wrong had nothing to press.

<Callout type="warn">
**This replaces changes you made to the agent** — but it does not destroy them. The live definition is frozen as its own version first, tagged `agent-edited-…`, and only then overwritten. Watch for the **Edited** badge; the confirmation names what is about to happen.
</Callout>

So an edit you want back is under [Versions](/platform/snapshots) with that tag: read it, copy from it, or deploy it again. The tag is derived from the definition's content, so reinstalling twice from the same edited state reuses one version rather than piling up near-identical ones — and an unedited reinstall freezes nothing at all.

## Trace him

**He installs with tracing already on**, so his runs are under [Traces](/platform/traces) from the first one — every model call, every tool call, every block.

That is the opposite of the default for anything you build, and for the same reasons. [Tracing is off by default](/platform/deployments#tracing) because it costs throughput, and a chat agent answering a handful of questions has none to lose. What he does have is the ability to deploy, and a diet of text other people wrote — so "what did he actually do, and was he told to" is worth being able to answer about every run rather than only the ones after somebody thought to switch it on.

Turn it off with the toggle if you would rather. That is a decision, and it sticks: a redeploy or a roll-out afterwards leaves it off rather than quietly restoring the default.

Expect his pods to be replaced either way: the runtime reads the tracing setting when it starts, so it cannot be changed in place. Nothing else about the deployment changes — same version, same environment.

## Give him more turns

One answer is a loop: he calls a tool, reads what came back, and decides what to do
next. Each pass through that loop is a **turn**, and there is a limit on how many one
answer may take. Reaching it ends the run without an answer, and the panel says he
ran out of steps.

He ships with a limit of **60**, which is enough for the work he is usually asked to
do — read the traces for a failing deployment, work out why, write a fix, prove it
with a test suite. Raise it under **Admin → Platform agent** if the tasks you give
him are longer than that, or lower it to cap what a stuck run can spend before the
guardrail catches it. Anything from **1 to 200** is accepted. Leave the field empty
to use the limit his definition ships with; clearing it is how you get back to that
after setting a number.

It is a ceiling and not a budget: an answer that takes four turns takes four. What a
higher limit costs is the tail — a genuinely stuck run burns the whole allowance
before it stops.

Applying it replaces his pods, the same as tracing and for the same reason: the
runtime reads the limit when it starts.

## Remove him

Press **Remove** to undeploy him. The integration is **kept**, so any changes you made survive and installing again reuses them — this is the reversible half.

To delete the integration as well, call the API with `?purge=1`. That also removes his skill resources and the cluster secret holding the provider key. It is the irreversible half, which is why it is deliberately not a button.

## His workspace

Dr. Octo can try a fix rather than describe one. He runs on the
[agentic runner](/deploy/docker-images#octo-agenticrunner) — a heavier image than
the one your integrations get, carrying a shell, `curl`, `jq`, the standalone
`octo` CLI, `dolphin`, and a scratch directory at `/workspace`.

That gives him a loop instead of an opinion: write a definition and a
`_test.yaml` suite beside it, run the suite, read the failures, fix, run it
again — and invoke a single flow when he wants to see what it actually returns.
Ask him to write a flow and he can hand you one he has watched pass.

Three things to expect from it:

- **The workspace is scratch.** It is an `emptyDir` that dies with his pod, capped at
  100Mi. Anything worth keeping he saves back through the API as a real
  integration; nothing in there survives a restart, and he will tell you so.
- **A flow he invokes runs standalone.** In-process queues, in-memory KV, no
  cluster resources, no connectors reaching anything he was not given. It proves
  the shape of a definition and the logic in it — never what your deployment
  would see. He is told to say which of the two he has shown you.
- **Commands are bounded.** Each one is killed after two minutes, so there is no
  `octo run` and nothing long-lived. He invokes once, or runs a suite.

He is deployed on that runner automatically. On an installation whose chart does
not configure it, **Install** is blocked with the reason shown rather than
producing a pod that crash-loops — he does not merely prefer the image, his
definition does not load without it.

## Restrict what he can do

Because he is an integration you can edit, set the limit on what he may do in his own definition rather than with a flag on the orchestrator. Open him in the editor, find the `octo_api` tool — a [`rest-dynamic`](/reference/connectors/http) block, inside the `platform_operator` specialist, and the only unrestricted one in the file — and add either setting:

```yaml
- type: rest-dynamic
  settings:
    connector: octo
    method: body.method
    path: body.path
    # Empty by default. Either of these narrows what he may call.
    allowMethods: [GET]
    pathPrefix: /integrations
```

Use `allowMethods: [GET]` to make him read-only, or `pathPrefix` to confine him to one part of the API. Save and roll out, and the restriction is live.

You do not need to defend the host: the connector's `baseURL` is a boundary he cannot cross whatever the block says, because a dynamic path resolves against it and no rendered path can redirect the call elsewhere.

His `logs_api` tool is a second, independent boundary — a different connector with a different `baseURL` — so narrowing one does nothing to the other. It already ships with `allowMethods: [GET]`, which costs nothing there because the observability API serves no other method. To take stored logs and traces away from him entirely, untick the observability grant and roll out; that removes the address rather than the tool, and he will say so when asked.

### The command tools are a different kind of thing

Everything above narrows an *address*. The [workspace](#his-workspace) tools do not have one, and it is worth being exact about what that means.

**Deleting a tool is the control that works.** `http_fetch`, `run_command`, `invoke_flow` and the rest are blocks in a definition you can edit, exactly like `octo_api`. Remove the block, save, roll out, and the capability is gone. That is the honest lever, and it is the one to reach for.

**The `allow` list on those blocks is a guardrail, not a boundary.** It names the five programs he may run, which keeps the ordinary path predictable and his traces readable. It does not contain him: `octo` is on that list, and `octo invoke` runs whatever definition it is pointed at — including one written into his workspace a moment earlier. Anything reachable from that pod is reachable from that tool.

**So the boundary is the pod.** What it holds is its own environment, which for him means his provider key, and it carries only the runtime ServiceAccount — no cluster credentials beyond leases. That is the blast radius, and it is why the agentic runner is a per-deployment choice rather than something every integration gets.

**`http_fetch` is the genuinely new reach.** Before it, his outbound access was two `baseURL`s and his model provider. Now it is anything his pod can route to — other integrations' internal Services, and on a cloud node the instance metadata endpoint. He is restricted to `http` and `https`, which is what stops `file://` reading his own pod, but nothing in his definition restricts *hosts*. If that matters on your cluster, a NetworkPolicy on his deployment is the control; his definition is not.

<Callout>
Bear in mind that he reads integration definitions, resource contents, pod logs and — with the observability grant — stored log messages and captured request bodies from every deployment. All of that is text other people wrote, which makes prompt injection a real consideration: a malicious string in a flow definition, or in a log line an integration was made to emit, is an instruction he may see. Narrow `allowMethods` to bound what such an instruction could achieve, delete the command tools if the loop above is not worth that reach on your installation, untick the observability grant if you would rather he did not read that surface at all, and leave tracing on — it is on by default precisely so that "was he told to do that" is answerable after the fact rather than only from the run you happened to be watching.
</Callout>

## What he is made of

Read this before you change him. The whole file is in the editor.

| Piece | What it does |
| --- | --- |
| `chat` flow | An HTTP source on `/chat` with [server-sent events](/reference/connectors/http) enabled, so answers stream a token at a time |
| `ai-agent` block | The coordinator: streaming, `agentId: dr-octo`, memory keyed to the signed-in user and the conversation, a 500k-token window and summarising compaction, and `userMemory` on. `stopWhen` reads the `X-Agent-Stop` header, which is how the panel's Stop reaches a run [it is not connected to](/ai/agent-signals). Two more `ai-agent` blocks sit in its tool slots — see [the two specialists](#the-two-specialists) |
| `nameThread` slot | On the coordinator, and all that is left of the recording pipeline: on the opening exchange only, asks `llm-fast` for a name for the conversation. The engine writes it — see [Naming a conversation](/reference/blocks/ai#naming-a-conversation). The record itself is the runtime's |
| `octo_read` | Reads the orchestrator's [API](/platform/api-reference) — `allowMethods: [GET]`, so the coordinator can answer a question but not change anything |
| `integration_builder` | The first specialist (see [below](#the-two-specialists)): writes a definition and proves it |
| `platform_operator` | The second specialist: everything that changes the installation, and everything about what already happened |
| `send_email_report` | Sends an HTML report through the platform's own [email settings](/platform/admin-settings); the sender identity is the installation's, never the model's |
| `navigate_to` | Moves your browser to a page, when the answer to a question is a page |
| `check_expression` | Evaluates one [CEL](/reference/cel) expression, so he can prove one rather than assert it |
| `remember`, `forget`, `search_memory` | Built into the runtime rather than written here. What he has already remembered about you is placed in every request, so there is no tool to call to recall it |
| Skills | Seven documents on flow files, blocks, connectors, expressions, testing, the platform and email reports, loaded on demand rather than sitting in every prompt |

### The two specialists

The coordinator keeps the cheap things — a read-only API call, a CEL check, navigation, the built-in memory tools, and the mail tool — and delegates the work to two `ai-agent` blocks standing in its tool slots — a subagent here is just that: a tool whose process chain happens to be another agent, with its own prompt, its own tools and its own loop. It writes a brief, the specialist works, and one report comes back as the tool result.

| Specialist | Holds | For |
| --- | --- | --- |
| `integration_builder` | `read_workspace_file`, `write_workspace_file`, `list_workspace`, `invoke_flow`, `run_flow_tests`, `builder_check_expression`, `run_command`, `builder_octo_read` | Writing and **proving** a definition: draft into the [workspace](#his-workspace), run the [dolphin](/testing) suite, read the report, fix, run again. Its API tool is GET-only, so nothing it produces is saved |
| `platform_operator` | `list_api_operations`, `read_api_docs`, `octo_api`, `list_logs_operations`, `read_logs_docs`, `logs_api`, `http_fetch`, `refresh_platform_ui` | Changing and inspecting the installation: saving a definition, version tags, deploys, rollouts, scaling, secrets — and every question about stored logs and traces. Its prompt carries a map of the API's routes, so it does not rediscover them from the OpenAPI on every call |

Each specialist keeps its own conversation while yours is going on:
`memoryThreadId: vars.toolScope` with `memoryVolatile: true`, which is the
[scope the runtime mints](/reference/blocks/ai#what-a-tool-branch-is-told) for a
tool branch. So a second delegation in the same chat reaches the same builder,
with the definition it drafted a moment ago still in front of it — and none of it
touches the conversation you are having, or the store that is backed up. It is
scaffolding, and it evicts.

Three things the split buys, none of which a single twenty-tool agent could have:

- **A prompt each.** "How to write a definition and prove it" and "how this installation is deployed and diagnosed" want different instructions, and a single prompt carrying both is mostly irrelevant on any given turn.
- **A working context each.** A builder's loop fills a transcript with YAML drafts and test reports; an operator's fills with API responses. Kept apart, neither pays to re-read the other, and the conversation you are having stays short — what comes back to it is one report, not forty tool results.
- **A boundary.** There is exactly one unrestricted `octo_api` in the file and it is inside the operator, so a write to the platform is always a deliberate delegation.

What it costs: a delegation is a whole model run, and the panel is quiet while it works — which is why the SSE route's `maxDuration` is 30 minutes, and why the coordinator is told to answer from `octo_read` when that is the whole answer. The specialists cannot see your conversation — only their own work on it — so a thin brief comes back as a specialist guessing confidently. Both facts are in the coordinator's prompt because both are how this arrangement fails.

Each specialist emits its `tool_call` and `tool_result` events to the same stream the coordinator's go to, so the panel shows what it is doing rather than one chip sitting open for two minutes.

### What he remembers

He uses the runtime's [agent memory](/ai/agent-memory) — `agentId: dr-octo`, with `userMemory` on — so none of this is written in his definition any more. Three things are stored, and they are not the same thing:

| | What it is |
| --- | --- |
| **Working memory** | The transcript he re-reads. Compacted as it grows: `memoryCompaction: summarize` folds the early turns into a summary of them |
| **Conversation history** | What you can come back to. **Never compacted**, so it is what was actually said rather than the shortened version he still carries |
| **Facts** | What outlives a conversation — how you like flows written, which integration is yours, what to call you |

All three live in the orchestrator's own tables, keyed on the **integration**. That is what makes them survive a redeploy — and a reinstall, which used to destroy every conversation on the installation because the store was scoped to the deployment.

Expect three things of it:

- **Facts are yours.** They are keyed on the user the platform authenticated, which he can neither see nor set — `userId` is resolved by the flow from an identity the chat route writes server-side. Another person's conversation cannot reach them however he is asked.
- **He does not have to look them up.** What he has already remembered is placed in every request, so there is no recall tool to call and no turn where he forgets to. Past a bound the rest stay reachable through `search_memory`.
- **Correcting a fact replaces it.** Remembering under a name that already exists overwrites it, so telling him something has changed works the way saying it does.

Tell him to forget something and he will, but treat that as housekeeping rather than a privacy control: what he already said in a conversation is in that conversation, and a fact he was told not to keep may still be in the transcript. Erasing the conversation from [the memory viewer](/platform/admin-settings#agent-memory) removes both, and so does purging the agent.

## Run him yourself

He is a normal octo app, so run him standalone:

```bash
# llm-anthropic | llm-openai | llm-gemini | llm-openrouter
export LLM_CONNECTOR_TYPE=llm-anthropic
export LLM_API_KEY=sk-ant-...
export LLM_MODEL=claude-sonnet-4-6
export ORCHESTRATOR_URL=http://localhost:8090
# Optional. Without it his logs tools answer that the access was not granted.
export LOGS_URL=http://localhost:8091

# Required. His workspace and the five programs he drives default to the agentic
# runner's paths, which do not exist here. These are not optional the way
# LOGS_URL is: a cli-run allow list is resolved when the flow is BUILT, so an
# entry pointing at a file that is not there fails the whole config on load
# rather than the first call that would have used it.
export AGENT_WORKSPACE=$(mktemp -d)
export AGENT_OCTO_BIN=$PWD/bin/octo
export AGENT_DOLPHIN_BIN=$PWD/bin/dolphin
export AGENT_CURL_BIN=$(command -v curl)
export AGENT_FIND_BIN=$(command -v find)
export AGENT_JQ_BIN=$(command -v jq)

bin/octo run --config orchestrator/agent
```

That build-time resolution is also why his definition names every program through
a variable rather than writing the path in the `allow` list. Change one to a
literal and he stops loading anywhere but the cluster — including in the
[dolphin suite](/testing) that ships beside him.

```bash
curl -N -X POST localhost:8080/chat \
  -d '{"threadId":"t1","message":"list my integrations"}'
```

Work this way when you are iterating on his prompt or a tool — it is far faster than rolling out to see the result.
