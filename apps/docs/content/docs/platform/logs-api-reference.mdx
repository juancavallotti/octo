The log aggregator serves a description of its own API, the same way the [orchestrator](/platform/api-reference) does. Everything the `/platform/logs` and `/platform/traces` views read goes through that API, so the description is the reference for querying stored telemetry yourself.

```bash
curl -sS "$LOGS_URL/openapi.json"
```

It is **OpenAPI 3.1**, generated from annotations on the handlers at build time, committed, and embedded in the binary. It is never generated at runtime, so what a running aggregator serves is exactly what was reviewed with the code that serves it.

<Callout>
The service is called `logs` everywhere — the binary, the image, the pod and the `LOGS_URL` other services reach it by — but it stores traces too. They live here because they are the same shape of problem, so one description covers both.
</Callout>

## The operation index

`/openapi/operations` is a compact list of every route — method, path, summary and tags:

```bash
curl -sS "$LOGS_URL/openapi/operations"
```

```json
[
  {
    "method": "GET",
    "path": "/logs",
    "summary": "List log events",
    "tags": ["logs"]
  }
]
```

Sorted by path, then method. Read this first to find the tag worth asking about, then fetch that tag's detail — which is exactly how the [platform agent](/platform/agent) uses it.

The tags are `logs`, `traces`, `stats`, `retention`, `meta` and `openapi`.

## Reading part of the document

Two filters, and they are mutually exclusive — supplying both is a `400`:

| Query | Keeps |
| --- | --- |
| `?tag=traces` | Operations carrying that tag |
| `?path=/traces` | Routes whose path starts with that prefix |

```bash
curl -sS "$LOGS_URL/openapi.json?tag=logs"
```

A filtered document is a **valid OpenAPI document**, not an excerpt: schemas are pruned to the ones the surviving operations can actually reach, following `$ref` transitively, so the result still resolves. An unknown tag yields a document with no paths rather than an error — nothing matched is an answer.

## What the API offers

Every query route is a `GET`. The three [retention](#data-retention) routes are the exception, and one of them deletes. Two things are worth knowing about the query side before you read the description itself.

**Paging is keyset-based.** `/logs` and `/traces` return at most `limit` rows (default 200, clamped to 1000). A page that came back full carries `next_before`; send it as `before=` for the page after it. Treat it as opaque — it names a `(timestamp, id)` pair, not a timestamp, because rows routinely share a timestamp and a timestamp-only cursor would either skip the ties or serve them twice.

**Trace payloads are optional.** `/traces/{traceId}` includes every record's captured body by default, and those payloads are the whole weight of a trace. Pass `bodies=0` when you are only drawing a waterfall, then fetch the one record you need from `/traces/{traceId}/records/{id}`.

## Pod stats

The [pod stats sidecar](/docs/platform/pod-stats) writes each production pod's own
metrics to Redis. These three routes read them back, and they are the only part of this
API not backed by Postgres — which is why they answer even when the log store is
unreachable.

| Route | Purpose |
| --- | --- |
| `GET /stats/{deploymentId}/pods` | Which pods have reported, and whether they still are |
| `GET /stats/{deploymentId}/metrics` | The catalogue: every series name and label set, no samples read |
| `GET /stats/{deploymentId}/series` | The data |

Start at `/pods`. It names the pods the other two accept, and reports `liveRows` and
`rollupRows` separately: zero live rows beside a full history is the ordinary state of a
pod that stopped a few hours ago, because the live tier is kept for only twice the
rollup interval while the pod stays in the index for the whole retention window.

**`metric` is required on `/series`, and repeatable.** Samples are stored positionally
against a per-pod dictionary, so a query with no name filter reads every series of every
pod — around ninety-five of them, once a second. That filter is what bounds the
response, and `/metrics` is how you find exact names to put in it. Names match exactly;
`label=key=value` narrows within them and repeats are ANDed.

```bash
curl -sS "$LOGS_URL/stats/$DEPLOYMENT_ID/series?metric=process_resident_memory_bytes&from=2026-09-05T11:00:00Z"
```

**A counter's `value` is growth, on both tiers.** A Prometheus counter is cumulative, so
what is charted is how much it grew over the interval ending at that point. The history
tier stores that already; the live tier is differenced to match, so a chart never has to
know which tier answered. A counter that reads lower than the point before is treated as
a process restart rather than a negative delta. Pass `counters=absolute` for the raw
cumulative readings, or ask for the `last` stat on the rollup tier.

**`tier=auto` is the default** and resolves to `rollup` whenever the window reaches
further back than the live tier goes. That reach is `liveDepth × sampleInterval` — one
hour at the defaults — and a window older than it cannot be answered from live rows
however many are read, so serving it from live would look like data ending rather than a
tier that does not go back that far. The resolved tier and its step come back in the
response.

**Points are columnar, and `times` are unix milliseconds.** A series is thousands of
points, and a thousand RFC3339 strings is mostly punctuation for a number every chart
converts straight back to an integer. The window in the envelope stays RFC3339, and so
do the `from` and `to` parameters. Ask for only the numbers you need with
`stats=value,max`; the extra columns are rollup-only and omitted when not requested.

**A `null` reading is a gap, not a zero** — a series the dictionary knows that the scrape
did not report. On the rollup tier, `ends` is carried beside `times`: rows are not
contiguous, so a bucket's end not meeting the next one's start is where scraping stopped.

A deployment with no stats answers `200` with no items rather than `404`. This service
holds no deployment registry, so it cannot tell a deployment that never existed from one
whose sidecar is switched off or whose stats have expired, and a `404` would claim it
can. For the same reason a pod that cannot be read is reported in `warnings` and
skipped, never a failed request.

## Data retention

Stored telemetry grows without bound until you say otherwise. The policy that bounds it lives here rather than on the orchestrator, because this service owns the tables a sweep deletes from. Set it at [`/platform/admin/retention`](/platform/admin-settings#data-retention) unless you are automating it — these are the routes that page calls.

| Route | Purpose |
| --- | --- |
| `GET /settings/retention` | The two windows, in days, and when they were last changed |
| `PUT /settings/retention` | Set them |
| `POST /retention/run` | Enforce the stored policy now |

Two windows, because logs and traces have very different weights per day:

```bash
curl -sS -X PUT "$LOGS_URL/settings/retention" \
  -H 'Content-Type: application/json' \
  -d '{"logs_days":30,"traces_days":7}'
```

**Zero means keep forever**, on either axis, and zero is the default — so an installation that never sets a policy behaves exactly as it did before the feature existed. The upper bound is 3650 days.

A save replaces the whole policy, so **both fields are required** and a body naming only one is a `400`. That is deliberate: zero is a value here, not an absence, so a request mentioning only `logs_days` would otherwise read as "and switch trace retention off" — nobody means that by omission, and it is the direction that loses data.

A save deletes nothing. `POST /retention/run` is what deletes, and it reports what went:

```json
{
  "logs_deleted": 120412,
  "traces_deleted": 44980,
  "trace_summaries_deleted": 2211,
  "logs_cutoff": "2026-07-12T03:00:00Z",
  "traces_cutoff": null,
  "duration_ms": 8140
}
```

A `null` cutoff is how you tell an axis set to keep everything apart from one where nothing had expired — both report zero deleted. A policy that keeps everything is a `200` with zeros rather than an error: being asked to do nothing is an answer.

Only one sweep runs at a time, held by a Postgres advisory lock, so the nightly job and somebody pressing **Run now** cannot overlap. The loser gets a `409`.

Deletes are issued in batches and each commits on its own, so an interrupted sweep has simply deleted less — never something inconsistent — and the next run continues from there. A trace is deleted whole, and stored model prices are never swept; see [Traces](/platform/traces#retention) for why both of those matter.

### Running it nightly

The chart installs a CronJob that calls `POST /retention/run` at 03:00, controlled by `retention.enabled` (on by default) and `retention.schedule`. Because the policy defaults to keeping everything, that job is a nightly no-op until you set a window — turning retention on is a change to the policy, not to the release.

## Keeping it honest

The spec is regenerated in CI and the build fails if the committed copy differs, the same way it fails on unformatted code.

A separate test compares the routes registered in the source against the routes described in the spec, in **both** directions. Regenerating cannot catch a route that was added without annotations — it simply regenerates without it, identically — so a new route with no documentation fails that test by name.

## Authentication

There is none, on the same terms as the orchestrator. The aggregator is `ClusterIP` in the chart and trusts its callers; the platform BFF is the authorization boundary in front of it.

<Callout type="warn">
This means anything that can reach the aggregator's address can read every stored log line and trace payload on the install — which includes whatever your flows logged. Since the retention routes landed it can also **change the policy and delete that history**, with no confirmation and nothing to undo it. Keep it internal.
</Callout>

The browser never reaches any of this directly — the platform's server actions do, and they gate every call behind a session, with writes additionally behind `AUTH_WRITE_ROLES`. That variable [defaults to empty, meaning any signed-in user](/platform/admin-settings). Set it.
