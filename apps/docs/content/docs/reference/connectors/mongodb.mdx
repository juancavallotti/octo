The `mongodb` connector owns a MongoDB client — the connection string, credentials, and pool — and the `mongodb-*` blocks bind to it by name. It is the document-store counterpart to [`database`](/reference/connectors/database): where a row needs an explicit column mapping in and out, a message body is already a document, so storing a webhook payload is one block rather than a schema exercise.

**Provides a source:** no — it is a service connector. **Blocks that bind to it:** `mongodb-find`, `mongodb-insert`.

## `mongodb` connector

The connector opens the client on start and pings the deployment, so a malformed URI, a wrong credential, or an unreachable server fails at startup rather than on the first message. It disconnects on stop.

| Setting | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `uri` | string | Yes | — | Connection string, with no password in it: `mongodb://user@host:27017` or `mongodb+srv://user@cluster.example.net`. |
| `password` | string | No | — | Merged into the URI at startup, so only it has to be a secret — see below. |
| `database` | string | No | — | Database blocks address when they do not name one of their own. |
| `extendedJson` | enum `relaxed`\|`canonical` | No | `relaxed` | How BSON types cross the message boundary — see [BSON and JSON](#bson-and-json). |
| `maxPoolSize` | int | No | `32` | Connections the pool may open — see [Pool size and workers](#pool-size-and-workers). |
| `minPoolSize` | int | No | driver default (none) | Connections kept open while idle. |
| `maxConnIdleTime` | string | No | driver default (forever) | How long an idle connection is kept before it is closed, e.g. `5m`. |
| `timeout` | string | No | `30s` | Ceiling on a single operation, server selection included. |

```yaml
env:
  - name: MONGODB_PASSWORD
    required: true

connectors:
  - name: orders-db
    type: mongodb
    settings:
      uri: mongodb://app@db.internal:27017     # no secret here
      password: ${MONGODB_PASSWORD}            # the only secret
      database: orders
```

### Keeping only the password secret

The `password` setting is merged into the URI at startup, so the connection string — host, user, replica set, TLS options — can live in plain config and only the credential has to be a secret. Rotating it then touches one value instead of the whole URI. This is the same arrangement the [`database`](/reference/connectors/database) connector uses for its DSN.

A password already embedded in the URI is overridden by the setting, with a warning naming which value the connector used. A password with no username to attach it to is a startup error rather than a connector that starts and authenticates as nobody.

### Pool size and workers

`maxPoolSize` defaults to **32** because that is the worker count a flow gets by default — `max(8, GOMAXPROCS × 4)`, i.e. 32 on an eight-core host — so every worker of one flow can hold a checked-out connection instead of queueing on the pool. The driver's own default is 100, a number chosen with no knowledge of how much concurrency will actually arrive.

The connector cannot see which flows bind to it, so this is a starting point, not a derivation. Raise it when several flows share one connector; lower it when many runtime replicas point at a small server. A flow that sets its own `workers:` should be read alongside it.

A setting always wins over the same option spelled in the connection string, so there is one place to override whatever the URI says. A default only fills a gap neither of them filled: a URI carrying `?maxPoolSize=50` keeps its 50.

### BSON and JSON

BSON has types JSON does not: `ObjectId`, dates, `Decimal128`, and true 64-bit integers. Rather than flatten them — which would mean a document you read could not be handed back as a filter — this connector renders documents as [MongoDB Extended JSON v2](https://www.mongodb.com/docs/manual/reference/mongodb-extended-json/) in both directions.

In **relaxed** mode (the default), ordinary values stay plain JSON and only the types that need it are wrapped:

```json
{
  "_id":     { "$oid": "66b0f1a2c3d4e5f60718293a" },
  "created": { "$date": "2026-08-04T10:00:00Z" },
  "sku":     "A1",
  "qty":     2
}
```

The point is symmetry. That `_id` goes straight back into a filter as the shape it came out as:

```yaml
filter: '{"_id": {"$oid": body._id["$oid"]}}'
```

In **canonical** mode every value is typed — `{"$numberLong": "1500"}`, `{"$numberInt": "2"}` — which loses nothing at all, at the cost of turning every number into an object you have to reach into from CEL. Set `extendedJson: canonical` when documents carry `Decimal128` money or integer IDs above 2⁵³; leave it relaxed otherwise.

Input is parsed leniently in both modes, so a filter written in either form is accepted regardless of how results are rendered.

Two things to know when writing filters and documents as [expressions](/concepts/expressions):

- CEL numbers are doubles, so an integer literal above 2⁵³ cannot be written directly. Write it as `{"$numberLong": "9007199254740993"}` — a string the driver parses exactly.
- A date written unquoted in YAML is parsed as a timestamp and reaches the block as an RFC 3339 string. Quote it, or write it as `{"$date": "2026-08-04T10:00:00Z"}`.

### Addressing, and results

Every block names its `collection` as a CEL [expression](/concepts/expressions), and may name a `database` the same way — a flow serving several tenants routes `body.tenantId` (or similar) to a different collection per message, which a connector-wide constant could not do. An unset `database` uses the connector's.

And every block follows one rule for its result: **it becomes the message body**, unless you name a `resultVar`, in which case it goes there and the body is left alone. The body is the default because the result is usually the payload — an HTTP flow that ends in a find should answer with the documents. Naming a variable is how you say "keep the body I came in with".

## `mongodb-find` block

Read documents from a collection. Without `single`, the result is a list — `[]` when nothing matched, never `null`, so a [foreach](/reference/blocks/control-flow) over the body gets zero iterations rather than a type error.

| Setting | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `connector` | string | Yes | — | Name of the `mongodb` connector to use. |
| `collection` | CEL | Yes | — | Collection to read from. |
| `database` | CEL | No | the connector's | Database to read from. |
| `filter` | CEL | No | match everything | Query filter. |
| `projection` | CEL | No | whole documents | Fields to return, e.g. `{"sku": 1, "_id": 0}`. |
| `sort` | CEL | No | unsorted | Sort order — see below. |
| `limit` | int | No | all | Most documents to return. |
| `skip` | int | No | `0` | Documents to skip before returning any. |
| `single` | bool | No | `false` | Return the first match rather than a list. |
| `resultVar` | string | No | — | Store the result here instead of in the body. |

```yaml
process:
  - type: mongodb-find
    settings:
      connector: orders-db
      collection: '"orders"'
      filter: '{"status": "open", "customer": body.customerId}'
      sort: '[{"created": -1}]'
      limit: 20
```

With `single: true` the block returns the first matching document rather than a list, and **null when nothing matched** — an ordinary answer a flow branches on, not an error. This mirrors the [`sql`](/reference/connectors/database) block's `single`.

```yaml
  - type: mongodb-find
    settings:
      connector: orders-db
      collection: '"orders"'
      filter: '{"_id": {"$oid": body.orderId}}'
      single: true
```

### Sorting by more than one key

MongoDB applies sort keys in the order they are written, and a CEL object cannot carry that order — CEL maps are unordered, and the JSON on the way to BSON sorts keys alphabetically. So a multi-key object is **refused at runtime** rather than silently reordered; write a list of single-key objects instead:

```yaml
sort: '[{"created": -1}, {"sku": 1}]'     # created descending, then sku ascending
sort: '{"created": -1}'                   # fine: one key has no order to lose
sort: '{"created": -1, "sku": 1}'         # error: which key sorts first is unknowable
```

## `mongodb-insert` block

Write documents into a collection. `document` decides how many by what it evaluates to: an object writes one, a list of objects writes them all. The value already says which, so there is no mode setting to keep in sync with it.

Because a message body is already a document, storing an inbound payload is `document: body`.

| Setting | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `connector` | string | Yes | — | Name of the `mongodb` connector to use. |
| `collection` | CEL | Yes | — | Collection to write to. |
| `database` | CEL | No | the connector's | Database to write to. |
| `document` | CEL | Yes | — | An object, or a list of objects. |
| `unordered` | bool | No | `false` | Keep going after a document fails, rather than stopping at the first. Lists only. |
| `resultVar` | string | No | — | Store the result here instead of in the body. |

```yaml
process:
  - type: mongodb-insert
    settings:
      connector: orders-db
      collection: '"orders"'
      document: body
```

The result is `{insertedCount, insertedIds}`. `insertedIds` is always a list, even for one document, so a flow reading it does not have to branch on how many were written — and the ids are rendered as extended JSON, so an `_id` the server generated comes back in the shape a filter takes:

```yaml
  - type: mongodb-insert
    settings:
      connector: orders-db
      collection: '"orders"'
      document: body
      resultVar: written
  - type: mongodb-find
    settings:
      connector: orders-db
      collection: '"orders"'
      filter: '{"_id": vars.written.insertedIds[0]}'    # no conversion needed
      single: true
```

An empty list inserts nothing and returns `{insertedCount: 0, insertedIds: []}` rather than failing, so a flow inserting whatever it filtered out of a payload keeps working on the day the payload filters down to nothing.

A batch that fails may still have written part of itself — always with `unordered: true`, and up to the failing document without it. The flow fails either way, but the error says how many landed, because "insert failed" and "insert half-failed" call for different recoveries.
