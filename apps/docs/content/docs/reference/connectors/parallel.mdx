The `parallel` connector holds the API key and talks to [Parallel](https://parallel.ai), a web research API built for agents. Its search endpoint answers in the same request with ranked pages and the excerpts Parallel picked out of them.

## `parallel` connector

**Provides a source:** no — it is a service connector. **Blocks that bind to it:** `parallel-search`.

### Settings

| Setting | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `apiKey` | string | Yes | — | Authenticates with the Parallel API; source it from `${PARALLEL_API_KEY}`. Never logged. |
| `webhookSecret` | string | No | — | Verifies inbound webhooks. Take it from **Settings → Webhooks** on the Parallel platform, `whsec_` prefix included. |
| `timeout` | duration | No | `30s` | Bounds each Parallel API call. |

An `apiBaseURL` setting also exists to override the API base (default `https://api.parallel.ai`), mainly for tests; it is not exposed in the editor.

```yaml
env:
  - name: PARALLEL_API_KEY
    required: true

connectors:
  - name: research
    type: parallel
    settings:
      apiKey: ${PARALLEL_API_KEY}
```

A `whsec_`-prefixed secret carries base64 key material rather than the key itself, so the connector decodes it at **startup**. A malformed one fails the service immediately, rather than becoming a signature that silently never matches.

### Error handling

Parallel signals errors with an HTTP status ≥ 400 carrying a `detail` field. Every block has a `failOnError` setting (default `true`): when true, a Parallel error [fails the flow](/concepts/error-handling); when false, the message passes through unchanged.

### Where the result goes

Every block follows the same convention as [pinecone](/reference/connectors/pinecone): the response becomes the **body**, because it is the payload the next block works on. Set `resultVar` to keep the incoming body and store the response in a variable instead.

## `parallel-search` block

**Parallel Search** — search the web and return ranked pages with LLM-optimized excerpts.

Parallel's search is not a keyword API. An **objective** says, in natural language, what the caller is actually after; the **queries** are the searches to run toward it. Parallel ranks results against the objective, which is why both are required.

| Setting | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `connector` | string | Yes | — | Name of the `parallel` connector to use. |
| `objective` | expression | Yes | — | CEL expression describing what the search is for. |
| `searchQueries` | expression | Yes | — | CEL expression for the queries to run: one string, or a list. |
| `mode` | enum | No | Parallel's `advanced` | `advanced` (~3s, best quality), `fast` (~700ms), or `turbo` (~250ms). |
| `processor` | string | No | — | Parallel processor to run the search on. |
| `maxResults` | int | No | Parallel's default | Number of results to return. |
| `maxCharsPerResult` | int | No | Parallel's default | Cap on the characters returned per result. |
| `resultVar` | string | No | — | Store the response here and leave the body; when empty, the response becomes the body. |
| `failOnError` | bool | No | `true` | Turn a Parallel API error into a flow error. |

```yaml
- type: parallel-search
  name: research
  settings:
    connector: research
    objective: body.question
    searchQueries: '[body.question]'
    mode: fast
    maxResults: 8
    resultVar: hits
```

**Response shape** — `search_id`, `results` (each with `url`, `title`, `publish_date`, and `excerpts`), plus `warnings`, `usage`, and `session_id`.

A setting left unset is omitted from the request, so Parallel's own default applies rather than this connector pinning one.
