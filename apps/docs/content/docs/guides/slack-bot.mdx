This guide builds a Slack bot that receives events over HTTP, verifies each
request's signature, answers Slack's URL-verification handshake, and replies to
@-mentions by name, following
[`samples/slack-bot.yaml`](https://github.com/juancavallotti/octo/blob/main/samples/slack-bot.yaml).

## Set up the Slack app

<Steps>
<Step>
Create a Slack app at [api.slack.com/apps](https://api.slack.com/apps). Under
**OAuth & Permissions**, give the bot the `chat:write`, `users:read`, and
`users:read.email` scopes, then install it to your workspace and copy the
**bot token** (`xoxb-...`).
</Step>
<Step>
Under **Basic Information**, copy the **signing secret**. Slack signs every
request with it, and the flow verifies that signature.
</Step>
<Step>
Under **Event Subscriptions**, subscribe the bot to the `app_mention` event and
point the **Request URL** at this service's `/slack/events` route. While
developing, expose your local port with a tunnel such as ngrok. Slack sends a
one-time verification challenge to the URL when you save it; the flow below
answers it automatically.
</Step>
<Step>
Export the credentials and run:

```bash
export SLACK_BOT_TOKEN=xoxb-...
export SLACK_SIGNING_SECRET=...
octo run --config samples/slack-bot.yaml
```
</Step>
</Steps>

## The connectors

The config declares the HTTP server that receives events and a `slack` connector
holding the credentials:

```yaml title="samples/slack-bot.yaml (excerpt)"
connectors:
  - name: api
    type: http
    settings:
      port: ${HTTP_PORT}

  - name: slack
    type: slack
    settings:
      botToken: ${SLACK_BOT_TOKEN}
      signingSecret: ${SLACK_SIGNING_SECRET}
```

## Capture the raw request

Slack signs the **exact request bytes**, so `rawBodyVar` copies the raw body
into a variable and `headers` captures Slack's two signature headers.

```yaml title="samples/slack-bot.yaml (excerpt)"
source:
  connector: api
  type: http
  settings:
    path: /slack/events
    headers: [X-Slack-Signature, X-Slack-Request-Timestamp]
    rawBodyVar: rawBody
```

## Verify, then handle

The first block authenticates the request; the rest branches between Slack's
one-time handshake and real events:

```yaml title="samples/slack-bot.yaml (excerpt)"
process:
  # 1. Authenticate the request (aborts on a bad or stale signature) and
  #    flag Slack's URL-verification handshake.
  - type: slack-verify-request
    name: verify
    settings:
      connector: slack

  # 2. Either echo the URL-verification challenge, or handle the event.
  - type: if
    name: challenge-or-event
    condition: has(vars.slackChallenge)
    then:
      process:
        # Slack's one-time handshake: reply 200 with the challenge value.
        - type: set-payload
          settings:
            value: '{"challenge": body.challenge}'
    else:
      process:
        # Keep only @-mentions, ignoring the bot's own messages.
        - type: slack-event
          name: mentions
          settings:
            eventTypes: [app_mention]
            filter: body.botId == null
        # Resolve the mentioning user (users.info) into vars.slackUser.
        - type: slack-lookup-user
          name: whois
          settings:
            connector: slack
            by: id
            user: body.user
        # Reply in the same channel, greeting the user by name.
        - type: slack-send-message
          name: reply
          settings:
            connector: slack
            target: body.channel
            text: '"thanks " + vars.slackUser.real_name + ", you said: " + body.text'
```

`slack-verify-request` recomputes the HMAC signature over `vars.rawBody` with
the connector's signing secret and aborts the flow on a mismatch or a stale
timestamp. When the request is Slack's `url_verification` handshake, it sets
`vars.slackChallenge` so the flow can branch; the challenge branch replies with
`{"challenge": body.challenge}`, which is what Slack expects to confirm your
Request URL.

`slack-event` filters the event stream: `eventTypes` keeps only `app_mention`,
and the CEL `filter` drops messages sent by bots (`body.botId == null`) so the
bot never answers itself. It also flattens the event into `body.user`,
`body.channel`, `body.text`, `body.ts` and `body.threadTs`, with the untouched
original under `body.raw`.

`slack-lookup-user` calls `users.info` for the mentioning user and stores the
user object in `vars.slackUser` (`by: email`, the default, looks up by email
address). `slack-send-message` posts to `target`, a channel ID such as
`body.channel`, and stores the sent message's timestamp in `vars.slackTs`.

### Reply in a thread

To answer in a thread, pass the triggering message's timestamp as `threadTs`:

```yaml
- type: slack-send-message
  settings:
    connector: slack
    target: body.channel
    threadTs: body.ts
    text: '"on it!"'
```

For a message that is already in a thread, use its `body.threadTs` so the reply
lands in the same thread rather than starting a new one.

## Handle a slash command

Slack posts slash commands (`/deploy staging`) and interactivity (buttons,
modals, shortcuts) form-encoded rather than as JSON, so the http source must
keep the body as raw content with `rawBody: true`.
[`samples/slack-slash-command/`](https://github.com/juancavallotti/octo/tree/main/samples/slack-slash-command)
acknowledges `/deploy` at once and reports the result later:

```yaml title="samples/slack-slash-command/config.yaml (excerpt)"
source:
  connector: api
  type: http
  settings:
    path: /slack/commands
    headers: [X-Slack-Signature, X-Slack-Request-Timestamp]
    rawBody: true
process:
  - type: slack-verify-request
    name: verify
    settings:
      connector: slack
  - type: if
    name: known-command
    condition: body.command == "/deploy" && body.text != ""
    then:
      process:
        - type: queue-dispatch
          name: enqueue
          settings:
            subject: '"slack-deploy"'
        - type: set-payload
          name: ack
          settings:
            value: >-
              {"response_type": "ephemeral",
               "text": "Deploy to " + body.text + " requested by <@" + body.user_id + ">"}
    else:
      process:
        - type: set-payload
          name: usage
          settings:
            value: '{"response_type": "ephemeral", "text": "Usage: /deploy <environment>"}'
```

After verifying the signature, `slack-verify-request` parses the form into
`body`, so Slack's fields read directly: `body.command`, `body.text`,
`body.user_id`, `body.channel_id` and `body.response_url`. For an interactivity
request, which carries a single `payload` field holding JSON, `body` becomes
that JSON, so `body.type` and `body.actions` read directly too.

The flow's response body is the immediate reply: `response_type: ephemeral`
shows it only to the caller, and `in_channel` posts it for everyone.

### Reply later through `response_url`

Slack shows the caller an error unless the command is answered within 3
seconds, so the flow above only queues the work and acknowledges it. The
fire-and-forget `queue-dispatch` hands a worker the parsed command, and the
worker answers on `response_url`, which Slack accepts for 30 minutes:

```yaml title="samples/slack-slash-command/config.yaml (excerpt)"
connectors:
  - name: slack-hooks
    type: http-client
    settings:
      baseURL: ${SLACK_HOOKS_URL}   # defaults to https://hooks.slack.com

flows:
  - name: deploy-worker
    source:
      type: queue
      settings:
        subject: slack-deploy
    process:
      - type: rest-dynamic
        name: report
        settings:
          connector: slack-hooks
          method: '"POST"'
          path: body.response_url.replace(env.SLACK_HOOKS_URL, "")
          allowMethods: [POST]
          pathPrefix: /commands
          body: >-
            {"response_type": "in_channel",
             "text": "<@" + body.user_id + "> deployed to " + body.text}
```

`rest-dynamic` resolves the path against the connector's base URL and refuses a
full URL, so stripping the webhook host from `response_url` is also the check
that the reply goes to Slack: a `response_url` on any other host keeps its
host, and the block fails without making a request.

To try it, add a `/deploy` slash command to your Slack app with its Request URL
pointing at `/slack/commands`, run the sample with
`task run:sample -- slack-slash-command`, and type `/deploy staging`.

## Try it

Mention the bot in a channel it has been invited to:

> @yourbot hello there

The bot replies in-channel: `thanks Ada Lovelace, you said: <@U123ABC> hello there`.

<Callout type="warn">
  Slack expects a 2xx within **3 seconds**, or it retries the event. Acknowledge
  first and offload slow work (LLM calls, database writes) with
  `queue-dispatch`. See [Events and Queues](/guides/events-and-queues).
</Callout>
