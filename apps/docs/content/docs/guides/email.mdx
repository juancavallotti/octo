This guide builds a support mailbox that answers every message from a person and files it away. It also adds an hourly digest that reads the answered mail without changing anything. It follows
[`samples/email/`](https://github.com/juancavallotti/octo/tree/main/samples/email).
For every setting, see the [Email reference](/reference/connectors/email).

## Run it

<Steps>
<Step>
Create a folder named `Answered` in the mailbox.
</Step>
<Step>
Export the account's details. The sample uses one server for IMAP (implicit TLS on port 993) and SMTP (STARTTLS on port 587):

```bash
export MAIL_HOST=mail.example.com
export MAIL_USER=support@example.com
export MAIL_PASSWORD=...
```
</Step>
<Step>
Run the sample, then send a message to the mailbox. A reply arrives within a minute, and the message moves to `Answered`.

```bash
octo run --config samples/email/config.yaml
```
</Step>
</Steps>

## Declare the connectors

Receiving and sending are separate protocols, so declare one connector for each. Both connectors use their protocol's default security: `tls` for `imap`, `starttls` for `smtp`.

```yaml title="samples/email/config.yaml (excerpt)"
connectors:
  - name: inbox
    type: imap
    settings:
      host: ${MAIL_HOST}
      username: ${MAIL_USER}
      password: ${MAIL_PASSWORD}

  - name: outbox
    type: smtp
    settings:
      host: ${MAIL_HOST}
      username: ${MAIL_USER}
      password: ${MAIL_PASSWORD}
```

If your server uses different ports or modes, set `security` (`none`, `starttls` or `tls`) and `port` on each connector.

## Run every new message through a flow

Bind a flow to the `imap` source. It polls every `interval`, runs each new message through the flow, and applies `onSuccess` only after the flow completes:

```yaml title="samples/email/config.yaml (excerpt)"
source:
  connector: inbox
  type: imap
  settings:
    interval: 1m
    onSuccess: move
    moveTo: Answered
```

If the flow fails, the message stays in the inbox, unseen, and the next poll reads it again. If you want to leave the mailbox untouched, set `onSuccess: none`. The source then keeps track of how far it has read, and starts from mail that arrives after it first runs.

The body is the received message: `body.from.address`, `body.subject`, `body.text`, `body.headers`, `body.attachments`, and the rest of the fields listed in [the received message](/reference/connectors/email#the-received-message).

## Reply in the same thread

Before replying, skip anything a robot sent. Out-of-office replies and bounces carry an `Auto-Submitted` header with a value other than `no`, and a bounce may have no sender at all. Mark your own reply the same way, so a robot on the other end doesn't answer it and start a loop:

```yaml title="samples/email/config.yaml (excerpt)"
- type: if
  name: from-a-person
  condition: 'body.from != null && (!("Auto-Submitted" in body.headers) || body.headers["Auto-Submitted"][0].lowerAscii() == "no")'
  then:
    process:
      - type: smtp-send
        name: reply
        settings:
          connector: outbox
          from: '"Support <" + env.MAIL_USER + ">"'
          to: body.from.address
          subject: '"Re: " + body.subject'
          inReplyTo: body.messageId
          headers: '{"Auto-Submitted": "auto-replied"}'
          text: >
            "Hi " + (body.from.name != "" ? body.from.name : "there") +
            ",\n\nThanks for writing. We received your message and will answer within one business day.\n"
```

`inReplyTo` threads the reply under the original in the sender's mail client. Every `smtp-send` setting except `connector` is a CEL expression. Set `html` beside `text` to send both versions, and set `attachments` to a list of files. A received `body.attachments` list can be passed through as is.

## Read the mailbox on a schedule

To read mail at a time the flow chooses, use `imap-fetch` instead of a source. The digest flow runs hourly from a cron schedule and reads what the autoreply flow filed in Answered since yesterday:

```yaml title="samples/email/config.yaml (excerpt)"
- name: digest
  source:
    connector: hourly
    type: cron
    settings:
      schedule: "@every 1h"
      payload: '{"since": string(now - duration("24h"))}'
  process:
    - type: imap-fetch
      name: answered
      settings:
        connector: inbox
        mailbox: Answered
        search: all
        since: body.since
        limit: 50
    - type: log
      name: report
      settings:
        message: '"answered since yesterday: " + string(size(body)) + " messages, " + string(size(body.filter(m, m.attachments.size() > 0))) + " with attachments"'
```

`imap-fetch` replaces the body with a list of messages. `since` matches on the date only, because IMAP searches by day, so this reads up to 50 matching messages received on or after yesterday's date, rather than exactly the last 24 hours. Its `onFetch` defaults to `none`, so the digest never marks, moves or deletes anything. A POP3 mailbox works the same way with the `pop3` source and `pop3-fetch`. POP3 has no folders, though, so it can only keep or delete messages.

## Test it

Sources don't run under `invoke`, so each test case supplies the body the `imap` source would have produced, and mocks the blocks that would reach the mail server:

```bash
dolphin test samples/email/autoreply_test.yaml samples/email/digest_test.yaml --env-file samples/.env.test
```

<Callout type="info">
Only the replica that holds the source's leadership starts a poll, so scaling the service doesn't make replicas compete for the same mail. A message can still run twice: if its flow outlives `flowTimeout`, if the service stops between a reply and the move to Answered, or if leadership moves while a message is being handled, the next poll reads it again. Keep `flowTimeout` above the time your flow takes.
</Callout>
