Four ways to get Octo, in increasing order of effort: download a
[prebuilt CLI](#download-the-cli), install it
[with `go install`](#install-with-go), run it [from Docker](#run-from-docker),
or [build from source](#build-from-source).

## Download the CLI

Every release publishes a statically linked `octo` binary for macOS, Linux, and
Windows on the
[GitHub releases page](https://github.com/juancavallotti/octo/releases/latest).

<Tabs items={['macOS', 'Linux', 'Windows']}>
<Tab value="macOS">

<DynamicCodeBlock lang="bash" code={`# Apple Silicon; use darwin_amd64 on an Intel Mac.
curl -fsSL -o octo.tar.gz \\
  https://github.com/juancavallotti/octo/releases/download/v${OCTO_VERSION}/octo_darwin_arm64.tar.gz
tar -xzf octo.tar.gz
sudo mv octo /usr/local/bin/octo`} />

If Gatekeeper blocks the first run, clear the quarantine attribute with
`xattr -d com.apple.quarantine /usr/local/bin/octo`.

</Tab>
<Tab value="Linux">

<DynamicCodeBlock lang="bash" code={`# x86-64; use linux_arm64 on arm.
curl -fsSL -o octo.tar.gz \\
  https://github.com/juancavallotti/octo/releases/download/v${OCTO_VERSION}/octo_linux_amd64.tar.gz
tar -xzf octo.tar.gz
sudo install -m 0755 octo /usr/local/bin/octo`} />

</Tab>
<Tab value="Windows">

<DynamicCodeBlock lang="powershell" code={`# x86-64; use windows_arm64 on arm.
Invoke-WebRequest -Uri https://github.com/juancavallotti/octo/releases/download/v${OCTO_VERSION}/octo_windows_amd64.zip -OutFile octo.zip
Expand-Archive octo.zip -DestinationPath .
# Move octo.exe somewhere on your PATH.`} />

</Tab>
</Tabs>

Each release also ships a `checksums.txt` with the SHA-256 of every archive:

<DynamicCodeBlock lang="bash" code={`curl -fsSL -O https://github.com/juancavallotti/octo/releases/download/v${OCTO_VERSION}/checksums.txt
sha256sum --ignore-missing -c checksums.txt`} />

Confirm the install:

<DynamicCodeBlock lang="bash" code={`octo version
# octo ${OCTO_VERSION} (built 2026-06-18T22:31:23Z)`} />

Continue to [Your First Flow](/getting-started/first-flow), or read
[Running Flows Locally](/runtime/running-locally) for `run`, `invoke`, and
`eval` in depth.

## Install with go

With a Go toolchain (1.27 or later), `go install` compiles and installs the CLI
into `$(go env GOPATH)/bin`:

```bash
go install github.com/juancavallotti/octo/runtime/octo@latest
```

Pin a release instead of tracking `@latest` by naming its tag:

<DynamicCodeBlock lang="bash" code={`go install github.com/juancavallotti/octo/runtime/octo@v${OCTO_VERSION}`} />

Make sure `$(go env GOPATH)/bin` is on your PATH, then confirm with
`octo version`.

<Callout type="info">
  Binaries installed this way do not carry the build date that the released
  archives do, so `octo version` reports the version without it.
</Callout>

## Install dolphin

`dolphin` is octo's companion test runner: it drives the `octo` CLI to unit-test
an integration. It ships from the same release through the same two channels:

<DynamicCodeBlock lang="bash" code={`# A prebuilt binary (Apple Silicon; swap the platform as above).
curl -fsSL -o dolphin.tar.gz \\
  https://github.com/juancavallotti/octo/releases/download/v${OCTO_VERSION}/dolphin_darwin_arm64.tar.gz
tar -xzf dolphin.tar.gz
sudo mv dolphin /usr/local/bin/dolphin

# Or, with a Go toolchain:
go install github.com/juancavallotti/octo/runtime/dolphin@latest`} />

dolphin runs the real `octo`, so it has to find one. It looks in three places
and stops at the first hit:

1. `$OCTO_PATH`: the binary itself, or a directory holding it
2. `./octo`: in the current directory
3. `octo`: on your PATH

<Callout type="warn">
  `$OCTO_PATH` is an override, not a hint. When it is set but does not name a
  runnable octo, dolphin fails instead of falling back to the other two.
</Callout>

Check both binaries, then run a real suite from a clone of the repository:

```bash
dolphin version
dolphin test samples/error-handling.yaml
```

```
ok   samples/error-handling_test.yaml  (charge-flowlevel)  73ms

2 passed, 0 failed, 0 errored, 0 skipped  (73ms)
```

From there, [your first test](/testing/first-test) writes one from scratch.

## Run from Docker

Two public images on [Docker Hub](https://hub.docker.com/u/juancavallotti),
both multi-arch (`linux/amd64` and `linux/arm64`) and published on every
release. Neither needs a cluster.

The runtime image runs your integrations only. Mount a directory of flow YAML at
`/etc/octo/integrations`; the runtime loads every `.yaml`/`.yml` in it and
serves HTTP sources on port 8080 by default:

```bash
docker run -p 8080:8080 -v "$PWD:/etc/octo/integrations" juancavallotti/octo-runtime
```

The editor image bundles the visual editor with the runtime. Flow YAML is read
and written in the directory you mount:

```bash
docker run -p 3000:3000 -v "$PWD:/work" juancavallotti/octo
```

Open [http://localhost:3000](http://localhost:3000). See the
[Editor Quickstart](/getting-started/editor-quickstart) for the tour, and
[Docker images](/deploy/docker-images) for what is inside each one.

## Build from source

### Prerequisites

- Go 1.27 or later.
- [Task](https://taskfile.dev), the repository's build runner
  (`brew install go-task` on macOS).
- pnpm, only for the web apps (editor, platform, docs). Not required for the CLI.

### Build the CLI

<Steps>
<Step>

#### Clone the repository

```bash
git clone https://github.com/juancavallotti/octo
cd octo
```

</Step>
<Step>

#### Build the binary

```bash
task runtime:build
```

This compiles both CLIs to `bin/octo` and `bin/dolphin`, stamping the build date
into each. `task runtime:build:octo` builds just the runtime.

</Step>
<Step>

#### Verify the build

```bash
bin/octo version
```

<DynamicCodeBlock lang="text" code={`octo ${OCTO_VERSION} (built 2026-06-18T22:31:23Z)`} />

The build date is stamped at link time, so yours will differ.

</Step>
<Step>

#### Add it to your PATH (optional)

The docs refer to the binary as `bin/octo` from the repo root. To run `octo`
from anywhere:

```bash
ln -s "$PWD/bin/octo" /usr/local/bin/octo
```

</Step>
</Steps>

<Callout type="info">
  The repo also ships runnable samples. Try one with
  `task run:sample -- hello-world.yaml`, or continue to
  [Your First Flow](/getting-started/first-flow) for the walkthrough.
</Callout>

Only a source build carries your local changes; released binaries and images are
cut from tagged commits by the [release pipeline](/deploy/releases-and-upgrades).
