The `octo` chart deploys the full platform — the editor UI, the orchestrator,
the log aggregator, Postgres and NATS — onto any Kubernetes cluster. It is
published as an OCI artifact on every release, so installing it needs no
checkout:

<DynamicCodeBlock lang="bash" code={`helm install octo oci://ghcr.io/juancavallotti/charts/octo \\
  --version ${OCTO_VERSION} \\
  --namespace octo --create-namespace \\
  --set ingress.host=octo.example.com \\
  --set postgres.auth.password=<strong-password>`} />

That command is complete on its own. The chart's defaults point at the public
Docker Hub images, and `image.tag` falls back to the chart's `appVersion`, so a
chart installs the images of its own release rather than drifting onto `latest`.

Both `--set`s are required rather than conventional: the chart has no default
host and no default password, because a published chart that defaults either one
is claiming a domain somebody else owns or shipping a credential everybody has.
Rendering fails, by name, if you leave them out. If your cluster has no default
IngressClass, add `--set ingress.className=<yours>` as well — see
[Ingress and TLS](#ingress-and-tls).

<Callout type="warn">
  **That command is a demonstration, not an install to keep.** `--set
  postgres.auth.password=…` puts the credential in Helm's release history, where
  it stays for every retained revision. For a deployment you intend to run,
  follow [Install on Kubernetes](/deploy/install-kubernetes): same chart, with
  every credential in a Secret you own and only its name in the values.
</Callout>

<Callout type="info">
  Prefer a cluster-specific starting point over the bare defaults — the profiles
  below carry the resource requests, security context and storage class each
  platform expects. See [GKE](/deploy/gke) and [EKS](/deploy/eks).
</Callout>

## What the chart deploys

| Component | Workload | Port | Notes |
|---|---|---|---|
| Platform (editor UI) | Deployment | 3000 | Exposed at `ingress.host`; proxies the orchestrator and logs APIs through its BFF |
| Orchestrator | Deployment + ServiceAccount + RBAC | 8090 | Deploys integrations through the Kubernetes API |
| Log aggregator | Deployment | 8091 | Consumes NATS `internal.logs` into Postgres; serves the logs query API |
| Postgres | StatefulSet + PVC | 5432 | Headless Service; credentials in a generated Secret. Skipped when `postgres.enabled=false` |
| NATS | StatefulSet (no volume) | 4222 / 8222 | Core NATS pub-sub; disable with `nats.enabled=false` |
| Redis | StatefulSet (no volume) | 6379 | Shared state between replicas of a component. Replace with a managed one via `externalRedis.url`; it cannot simply be turned off — see [Redis](#redis) |
| Schema applier | Job (Helm hook) | – | Runs `psql -f schema.sql` on every install and upgrade |
| Retention sweep | CronJob | – | Nightly `POST /retention/run` against the aggregator. Disable with `retention.enabled=false` |
| Runtime RBAC | ServiceAccount + Role | – | Lease permissions for integration pods (leader election) |
| Dev-run key | Secret | – | HMAC key for dev-run identity and hostnames. Only when `orchestrator.devRuns.enabled=true` |

Four images are not chart workloads. `octo-runtime` is passed to the
orchestrator as `RUNTIME_IMAGE`, and the orchestrator deploys one pod set per
integration from it at runtime; `octo-agenticrunner` is the alternative it
deploys for an integration that asked for the agentic runner
(see [Agentic runner](#agentic-runner)); `octo-devruntime` and `octo-devsidecar` are the
two containers of a *dev run* (see [Dev runs](#dev-runs)), created the same way. The schema Job is annotated
`helm.sh/hook: post-install,post-upgrade` with the `before-hook-creation` delete
policy, so it re-runs (idempotently) on every upgrade.

## How the chart is put together

`octo` is an application chart built on `octo-common`, a **library chart** that
holds every reusable template — naming, labels, image references, and the
generic Deployment / StatefulSet / Service / RBAC / Secret renderers. The
application templates are thin stubs that name a component and let the library
render it:

```yaml
# helm/templates/logs/deployment.yaml — the whole file
{{- include "octo-common.deployment" (dict "root" $ "component" "logs" ...) }}
```

The point is that a knob added once applies to every component and every target,
rather than being copied into five templates and drifting. Environment
variables are the deliberate exception: they are genuinely component-specific,
so each component keeps its own `_env.tpl`.

`octo-common` is vendored at `helm/charts/octo-common` and packaged inside the
`octo` tarball, so installing `octo` pulls nothing extra. It is also published
standalone (`oci://ghcr.io/juancavallotti/charts/octo-common`) if you want to
depend on it directly. Both charts carry the same version.

## Environment profiles

The chart ships a values file per target. Each is a starting point, not a
complete configuration — you still supply the hostname and a password.

| Profile | Target | Notable choices |
|---|---|---|
| `values-k3d.yaml` | Local k3d | NodePorts instead of an Ingress, `:dev` images, no TLS, database pinned to `./data` |
| `values-kind.yaml` | Local kind | As above, with kind's port mappings |
| `values-gke-autopilot.yaml` | GKE Autopilot | Requests **and** limits (Autopilot requires them), restricted security context, generous startup probes |
| `values-gke-standard.yaml` | GKE Standard | Requests without limits so pods can burst, zone spread for the editor |
| `values-eks.yaml` | AWS EKS | `alb` IngressClass, ACM certificate, `gp3` storage |

## Values

Defaults live in `helm/values.yaml`, where every knob is documented inline. The
ones that matter most:

### Images

| Key | Default | Purpose |
|---|---|---|
| `image.registry` | `docker.io/juancavallotti` | Registry base the per-component repositories are appended to. |
| `image.tag` | `""` | Shared tag. **Empty falls back to the chart's `appVersion`**, so a chart installs the images of its own release. |
| `image.pullPolicy` | `IfNotPresent` | Applied to all Octo images. |
| `<component>.image.repository` | `octo-<component>-paas` | Per-component override; `<component>.repository` still works. |
| `<component>.image.registry` | – | Per-component registry, overriding the shared one. |
| `<component>.image.digest` | – | Pin by digest. **Wins over any tag.** |

Components are `platform`, `orchestrator`, `logs`, `schema`, `runtime`,
`agenticrunner`, `devsidecar` and `devruntime`.
`postgres`, `nats` and `redis` also take `image.*`, but deliberately do **not**
inherit `image.registry` — that host holds the `octo-*` images only. Point their
own `image.registry` at a mirror for clusters that cannot reach Docker Hub.

Digest pinning is what the GCP release path uses: Cloud Build renders a values
file naming the exact digest of every image it pushed, so a release deploys what
that build produced rather than whatever a tag points at later. Render one
yourself with `task helm:values:images IMAGE_BASE=… TAG=…`.

### Per-workload knobs

Every workload accepts the same set, and `defaults:` applies them to all of
them at once. A per-component value overrides the default; the two are merged,
not replaced wholesale.

```yaml
defaults:
  resources:
    requests: { cpu: 100m, memory: 256Mi }
  securityContext:
    runAsNonRoot: true
    allowPrivilegeEscalation: false
    capabilities: { drop: ["ALL"] }

platform:
  resources:
    requests: { cpu: 250m, memory: 512Mi }   # only this component
```

Available on `defaults` and on each component: `resources`,
`podSecurityContext`, `securityContext`, `imagePullSecrets`, `nodeSelector`,
`tolerations`, `affinity`, `topologySpreadConstraints`, `priorityClassName`,
`podAnnotations`, `podLabels`, `extraEnv`, `envFrom`, `extraVolumes`,
`extraVolumeMounts`, `livenessProbe`, `startupProbe`, `revisionHistoryLimit`
and `strategy`.

The orchestrator and runtime additionally take
`serviceAccount.{create,name,annotations}` — that is where GKE Workload Identity
and EKS IRSA annotations go.

### Private registries

If you mirror the images somewhere that needs credentials, create the pull
Secret in the release namespace and name it once:

```yaml
defaults:
  imagePullSecrets:
    - name: regcred
```

That reaches all five chart workloads **and** the integration pods, which is the
part worth stating: those pods are created by the orchestrator at runtime, not by
this chart, so the value is passed to it as an environment variable rather than
rendered into a pod spec. Without it a mirrored install comes up entirely
healthy and every integration you deploy from that healthy editor sits in
`ErrImagePull`. Override it for the runtime image alone with
`runtime.imagePullSecrets`; empty there inherits `defaults`.

### Ingress and TLS

`ingress.tls.mode` is the biggest single difference between targets:

| Mode | Certificate comes from |
|---|---|
| `cert-manager` | A ClusterIssuer, issued per host over HTTP-01. What the k3s bootstrap provides. |
| `secret` | A TLS Secret that already exists — a pre-issued wildcard, or one Terraform placed. |
| `gke-managed-cert` | A Google-managed certificate; the chart creates the `ManagedCertificate`. |
| `acm` | An AWS ACM certificate by ARN, terminated at the ALB. |
| `none` | Terminated upstream; no TLS on the Ingress. |

Empty auto-selects `cert-manager` when a `clusterIssuer` is set, else `secret`.

#### Worked examples

Complete `values.yaml` files, one per mode — each renders and schema-validates
as shown. Install with `-f values.yaml`.

<Tab value="cert-manager">

A ClusterIssuer issues per host over HTTP-01: one certificate for the editor,
and one more for each integration you expose. What the k3s bootstrap provides.

```yaml
ingress:
  enabled: true
  className: nginx
  host: octo.example.com
  tls:
    mode: cert-manager
    clusterIssuer: letsencrypt-prod
    secretName: octo-tls

# Per-integration endpoints at {slug}.apps.example.com, each getting its own
# certificate from the same issuer as it is deployed.
orchestrator:
  baseDomain: apps.example.com
  ingressClass: nginx
  clusterIssuer: letsencrypt-prod

postgres:
  auth:
    password: CHANGEME
```

DNS for every host must already resolve to the ingress address, or the HTTP-01
challenge cannot complete. That includes each new subdomain, which is the reason
to prefer a wildcard once there is more than a handful.

</Tab>
<Tab value="Existing Secret">

Certificates issued by something else — bought, placed by Terraform, or synced
by external-secrets. The chart references and creates nothing.

```yaml
ingress:
  enabled: true
  className: nginx
  host: octo.example.com
  tls:
    mode: secret
```

covers every subdomain, so deploying an integration issues nothing and waits for
nothing.

### What answers an address nothing is deployed at

Set a `baseDomain` and every subdomain under it resolves, whether or not anything
is published there. Without help, a request to one that is not gets your ingress
controller's own answer — a white page with `404 page not found` on it — because
it never reaches anything octo runs.

`errorPages.enabled` (on by default) points those requests at the platform, which
serves a page naming what happened and showing the hostname that was asked for. It
adds no workload: the page is a route in the editor you already deploy.

It works by adding one catch-all route for `*.{baseDomain}`, written to lose to
every real deployment — exact hostnames win over the wildcard, and the chart pins
the precedence explicitly for each controller.

Which controller you run is read from `orchestrator.ingressClass`, matched a
segment at a time, so `traefik-public` and `internal-nginx` are recognised. If
yours is named something the fallback cannot place, name it directly — otherwise
the catch-all is **skipped** and you keep your controller's own 404 (the install
still succeeds, and `NOTES.txt` tells you):

```yaml
errorPages:
  controller: traefik   # nginx | traefik | alb
```

Turn the whole thing off if you would rather front the wildcard yourself:

```yaml
errorPages:
  enabled: false
```

To brand the backend-down cases too — a deployment restarting or failing to start,
which your controller answers with a bare 502 or 503 — also set:

```yaml
errorPages:
  backendErrors: true
```

That one is off by default because it works by adding annotations to **every**
deployment's own Ingress rather than adding a route beside them. Turn it on once
you have seen the 404 page working. It applies to ingress-nginx only: Traefik
expresses the same thing as an errors Middleware and ALB does not express it at
all, so on those classes it does nothing.

</Tab>

#### Where certificates come from

Three questions get conflated under "TLS", and they have different answers.

**1. Who issues — and who owns the issuer.** This chart never creates an
`Issuer` or `ClusterIssuer`. It names one, and the object belongs to whoever
runs cert-manager on the cluster. `clusterIssuer: letsencrypt-prod` is a
reference to something that must already exist; the k3s bootstrap in this repo
happens to create one by that name, which is why it appears in the defaults, and
it is not a name any other cluster is obliged to have.

**2. How the challenge is solved.** For ACME issuers (Let's Encrypt, ZeroSSL)
this is the choice that decides what you can issue:

| | HTTP-01 | DNS-01 |
|---|---|---|
| Proves control by | serving a token at `http://{host}/.well-known/acme-challenge/…` | writing a TXT record at `_acme-challenge.{host}` |
| Needs | public DNS pointing at the ingress, reachable on port 80 | API credentials for the DNS zone |
| Issues wildcards | **no** | **yes** |
| Works on a private cluster | no | yes |
| Per new subdomain | a fresh challenge, and a wait | nothing — the wildcard already covers it |

This is why `wildcardTLS.clusterIssuer` defaults to a *different* issuer from
`ingress.tls.clusterIssuer`: `*.{baseDomain}` can only be issued over DNS-01, so
it needs an issuer configured with a DNS solver, while the editor's own host is
happy with HTTP-01. Two issuers is not redundancy — it is the two things being
genuinely different.

<Callout type="info">
  On a Gateway API cluster with no ingress controller at all, an HTTP-01 issuer
  has nothing to create its challenge route with unless cert-manager is
  configured for Gateway API (`config.gatewayAPI.enabled=true`) so it can use the
  `gatewayHTTPRoute` solver. DNS-01 sidesteps that entirely and is the easier
  answer there.
</Callout>

**3. "Cloud certificates" are two unrelated mechanisms.** Both get called
"using the cloud's certificates", and they differ in where the private key
lives:

| Approach | Key lives | Setting | cert-manager |
|---|---|---|---|
| Google-managed certificate | the GCE load balancer | `tls.mode: gke-managed-cert` | not involved |
| AWS ACM | the ALB | `tls.mode: acm` | not involved |
| Let's Encrypt | a Secret in your namespace | `tls.mode: cert-manager` | yes |
| Google CAS / AWS Private CA | a Secret in your namespace | `tls.mode: cert-manager` + the annotations below | yes, plus that issuer's own controller |

The first two never produce a Kubernetes Secret at all — the certificate is
attached to the load balancer by annotation, which is why those Ingresses carry
no `tls` block and why neither mode has a Gateway API equivalent.

The last row is cert-manager issuing from a **private CA** rather than from a
public ACME CA — a corporate PKI, `GoogleCASClusterIssuer`, `AWSPCAClusterIssuer`.
These live outside the `cert-manager.io` API group, so the reference needs a kind
and a group as well as a name. Supply those two as annotations; the chart's own
issuer annotation does not collide with them:

```yaml
ingress:
  enabled: true
  className: nginx
  host: octo.example.com
  annotations:
    # Out-of-tree issuer. AWS Private CA is:
    #   cert-manager.io/issuer-kind: AWSPCAClusterIssuer
    #   cert-manager.io/issuer-group: awspca.cert-manager.io
    cert-manager.io/issuer-kind: GoogleCASClusterIssuer
    cert-manager.io/issuer-group: cas-issuer.jetstack.io
  tls:
    mode: cert-manager
    clusterIssuer: cas-prod      # the external issuer's name
    secretName: octo-tls
```

<Callout type="warn">
  That covers the editor's Ingress, where cert-manager's ingress-shim reads the
  annotations. The `Certificate` resources the chart writes itself — the
  `*.{baseDomain}` wildcard, and the editor's certificate for a chart-created
  Gateway — hardcode `kind: ClusterIssuer, group: cert-manager.io`, so an
  out-of-tree issuer cannot be named there.

  Set `wildcardTLS.clusterIssuer: ""` and write the `Certificate` yourself with
  whatever `issuerRef` you need. The chart then references
  `wildcardTLS.secretName` and issues nothing, which is exactly the seam for it.
</Callout>

`ingress.className` selects the controller (`traefik`, `nginx`, `gce`, `alb`);
`ingress.annotations` carries controller-specific behaviour. Per-integration
external endpoints are a separate axis — `orchestrator.baseDomain` plus
`orchestrator.ingressClass` and `orchestrator.ingressAnnotations`, which the
orchestrator stamps onto the Ingresses it generates at runtime.

Both class values default to **empty**, which omits `ingressClassName` and lets
whichever IngressClass the cluster marks default claim the Ingress. That is the
only portable default a published chart can have — naming a controller would
mint Ingresses that a cluster running something else never serves. Every
environment profile sets it explicitly, and so should you if your cluster has no
default IngressClass, or has one that is not the controller you want:

```bash
--set ingress.className=nginx --set orchestrator.ingressClass=nginx
```

<Callout type="warn">
  An Ingress that no controller claims is not an error anywhere. It is created,
  `helm install` succeeds, and the host simply never resolves to anything. If the
  editor is unreachable after an otherwise clean install, check
  `kubectl get ingress` for an empty `ADDRESS` and `kubectl get ingressclass` for
  which one — if any — is marked default.
</Callout>

### Gateway API

`networking.mode` selects which Kubernetes API publishes external endpoints —
both the editor's and the ones the orchestrator creates per deployed
integration. They are served by the same proxy, so it is one switch.

| Mode | Objects | Needs |
|---|---|---|
| `ingress` | `Ingress` per endpoint | Nothing — built into every cluster. The default. |
| `gateway` | `HTTPRoute` per endpoint, attached to a `Gateway` | The Gateway API CRDs. |

`gateway` covers kgateway, Envoy Gateway, Istio, Cilium, and the Gateway API
modes of ingress-nginx and Traefik.

<DynamicCodeBlock lang="bash" code={`kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.1/standard-install.yaml

helm install octo oci://ghcr.io/juancavallotti/charts/octo \\
  --version ${OCTO_VERSION} \\
  --namespace octo --create-namespace \\
  --set networking.mode=gateway \\
  --set networking.gateway.name=shared-gw \\
  --set networking.gateway.namespace=ingress \\
  --set ingress.host=octo.example.com`} />

Any Gateway API release from **v1.0 onwards** works, in the Standard channel —
`v1.6.1` above is simply the current one. The orchestrator builds against the
`gateway.networking.k8s.io/v1` types, GA since v1.0, and uses only Core-support
fields (`parentRefs`, `hostnames`, `rules.matches`, `rules.backendRefs`), so what
it sends is accepted unchanged across that range.

<Callout type="info">
  The Go module `sigs.k8s.io/gateway-api` is pinned lower than the CRDs you
  install, and deliberately: only the serialised shape of an `HTTPRoute` matters
  here, and it has not changed. Pinning the module forward would drag a
  `k8s.io/client-go` upgrade through the orchestrator for no change in the
  objects it produces.
</Callout>

**Attaching to an existing Gateway is the default, and is the point.** A Gateway
is cluster infrastructure: it predates the release, belongs to whoever runs the
proxy, and serves things unrelated to octo. Attaching means the cluster owner
owns the Gateway and octo owns only the routes in its own namespace — a much
easier permission conversation than "the orchestrator creates Ingresses", and
the orchestrator's Role reflects it, granting `httproutes` and nothing at all on
`gateways`.

It also removes configuration rather than moving it. An Ingress has no way to
say *attach me to that proxy*, so it must carry the ingress class, the
certificate arrangement and any controller-specific annotations itself — three
pieces of cluster configuration that have to be handed to the orchestrator and
stamped onto every object it creates. A route names its parent and its backend;
the listener owns the rest. So `orchestrator.clusterIssuer`,
`orchestrator.ingressClass`, `orchestrator.ingressAnnotations` and
`wildcardTLS`'s plumbing have no counterpart under `gateway`, and the chart
stops passing them.

| Key | Default | Purpose |
|---|---|---|
| `networking.gateway.name` | `""` | Gateway to attach to. **Required** unless `create` is true. |
| `networking.gateway.namespace` | `""` | Empty is the release namespace. A Gateway elsewhere must allow attachment from here via its listener's `allowedRoutes`. Cannot be combined with `create` — a Gateway this chart creates belongs to the release, so it has nowhere else to go, and the render refuses the pair rather than honouring half of it. |
| `networking.gateway.sectionName` | `""` | One listener by name. Usually unnecessary — a route attaches by hostname. Set it where one hostname is served by both an HTTP and an HTTPS listener, or the endpoint is also served in plaintext. |
| `networking.gateway.create` | `false` | Have the chart create the Gateway. |
| `networking.gateway.className` | `""` | `GatewayClass` for a created Gateway (`kgateway`, `envoy-gateway`, `istio`, `cilium`, `nginx`). **Required** when `create` is true. |
| `networking.gateway.annotations` | `{}` | Extra annotations on a created Gateway. |

<Tabs items={['Attach to an existing Gateway', 'Let the chart create one']}>
<Tab value="Attach to an existing Gateway">

The normal arrangement. The Gateway belongs to whoever runs the cluster's
ingress; octo adds routes to it and owns nothing else.

```yaml
networking:
  mode: gateway
  gateway:
    name: shared-gw
    namespace: ingress

ingress:
  enabled: true
  host: octo.example.com
  # className, annotations and tls are Ingress-only and ignored here — the
  # listener on shared-gw decides the controller and holds the certificate.

orchestrator:
  baseDomain: apps.example.com
  # clusterIssuer / ingressClass / ingressAnnotations have no counterpart in
  # this mode; the listener answers all three.

postgres:
  auth:
    password: CHANGEME
```

`shared-gw` needs a listener matching each hostname — `octo.example.com` and
`*.apps.example.com` — and its `allowedRoutes.namespaces` must permit this
release's namespace. Neither is something the chart can set from this side; both
are worth confirming with the Gateway's owner before installing.

</Tab>
<Tab value="Let the chart create one">

For the install with no Gateway to attach to. Listeners are derived: one per
editor host, plus the `*.{baseDomain}` wildcard.

```yaml
networking:
  mode: gateway
  gateway:
    create: true
    className: kgateway      # or envoy-gateway, istio, cilium, nginx

ingress:
  enabled: true
  host: octo.example.com
  tls:
    mode: cert-manager
    clusterIssuer: letsencrypt-prod
    secretName: octo-tls

orchestrator:
  baseDomain: apps.example.com

# Terminates the *.apps.example.com listener. DNS-01, because that is the only
# way to issue a wildcard — set clusterIssuer: "" instead if the Secret already
# exists.
wildcardTLS:
  enabled: true
  secretName: octo-wildcard-tls
  clusterIssuer: letsencrypt-dns

postgres:
  auth:
    password: CHANGEME
```

That renders a Gateway with two HTTPS listeners — `editor` for
`octo.example.com` against `octo-tls`, `integrations` for `*.apps.example.com`
against `octo-wildcard-tls` — plus a `Certificate` for each.

</Tab>
</Tabs>

`create: true` is for the install with no Gateway to attach to. Its listeners are
derived from what the release already publishes — `ingress.host`, and the
`*.{baseDomain}` wildcard integrations land on — with one listener per hostname,
so a route never has to name one. There is deliberately no listener override:
anything more elaborate is a Gateway you should own, with `create` left false.

**Certificates.** For a Gateway it created, the chart writes the editor's
`Certificate` itself rather than annotating the Gateway for cert-manager's
gateway-shim. The shim needs cert-manager installed with
`config.gatewayAPI.enabled=true` — not the default, so an annotation would render
everywhere and issue nothing on most clusters — and it creates one Certificate
per Secret a listener references with no per-listener opt-out, which would fight
the DNS-01 wildcard Certificate over the same Secret. On a Gateway you own, its
listeners and their certificates are yours; a Secret in the release namespace
could not be referenced from another without a `ReferenceGrant`.

Note that on a cluster with no ingress controller at all, an HTTP-01 issuer needs
cert-manager's `gatewayHTTPRoute` solver to complete a challenge. That is the
ClusterIssuer's configuration, not the chart's.

<Callout type="warn">
  A route that attaches to nothing — a misspelled Gateway, a listener that does
  not allow your namespace — is not an error anywhere. It is created,
  `helm install` succeeds, and the host resolves to nothing. This is the Gateway
  API version of the unclaimed-Ingress trap above, and it reports itself in one
  place:

  ```bash
  kubectl -n octo get httproute -o jsonpath='{.items[*].status.parents[*].conditions[*]}'
  kubectl -n ingress get gateway shared-gw -o jsonpath='{.status.listeners[*].attachedRoutes}'
  ```

  `Accepted=True` on the route and a non-zero `attachedRoutes` on the listener
  are what "it worked" looks like.
</Callout>

The orchestrator fails at startup, rather than at the first deploy, when it is
configured for Gateway API on a cluster without the CRDs. `gke-managed-cert` and
`acm` are refused at render time under `gateway`: both are Ingress annotations
naming a cloud load balancer's certificate, and neither has a Gateway API
equivalent.

#### Switching an existing release between modes

The chart's own objects swap over on `helm upgrade` — the editor's Ingress is
replaced by an HTTPRoute, and vice versa. **Deployments already running do not.**

The orchestrator publishes an endpoint when a deployment is *applied*, and
withdraws it through whichever publisher is configured *now*. So a deployment
created under `ingress` keeps its Ingress after the switch, and undeploying it
under `gateway` removes an HTTPRoute it never had — leaving the Ingress behind,
pointing at a Service that no longer exists and still claiming its hostname.

Redeploy each exposed integration after switching, then sweep up what the old
mode left:

```bash
# after switching to gateway
kubectl -n octo delete ingress -l app.kubernetes.io/managed-by=orchestrator
# after switching back to ingress
kubectl -n octo delete httproute -l app.kubernetes.io/managed-by=orchestrator
```

Withdrawing both kinds automatically would mean granting the orchestrator RBAC
on Ingresses *and* HTTPRoutes in both modes — losing the narrow permission set
that makes the Gateway API path worth having — and on a cluster with no Gateway
API installed, deleting an HTTPRoute is not a well-formed request at all. A mode
switch is a one-time migration, so it is one here too.

<Callout type="warn">
  **The editor needs a secure context.** Parts of it call browser APIs —
  `crypto.randomUUID` among them — that exist only over HTTPS or on `localhost`.
  Served over plain HTTP on any other hostname the pages still render, but
  client-side actions throw. `tls.mode: none` is for endpoints where something
  upstream terminates TLS, not for serving the editor unencrypted.
</Callout>

### Database

The chart runs Postgres itself by default, or points at a managed one.

| Key | Default | Purpose |
|---|---|---|
| `postgres.enabled` | `true` | Deploy the bundled StatefulSet. `false` skips it, its Service and its Secret. |
| `postgres.storage.size` | `5Gi` | PVC size. |
| `postgres.storage.storageClassName` | `""` | Empty uses the cluster default. |
| `postgres.storage.hostPath` | `""` | Pin the data to a fixed node path — single-node clusters only. See below. |
| `externalDatabase.host` / `.port` / `.database` / `.user` / `.sslmode` | – | Managed database coordinates, used when `postgres.enabled=false`. |

```yaml

  enabled: false

  host: octo.abcdef.us-east-1.rds.amazonaws.com

  user: octo
  sslmode: require
  existingSecret: rds-octo
  existingSecretPasswordKey: password
```

Prefer `existingSecret` over an inline password: values persist in Helm release
history. Either way the password never appears in a pod's environment as
plaintext — the chart passes it via `secretKeyRef` and lets Kubernetes expand it
into `DATABASE_URL`.

<Callout type="warn">
  **Storage on single-node clusters.** `local-path`-style provisioners name each
  volume's directory after the claim's UID, so recreating the cluster — or the
  claim — hands Postgres an empty directory while the old one stays on disk.
  `postgres.storage.hostPath` pins the data to a fixed path instead, and the
  chart creates a static `PersistentVolume` bound to it. Leave it empty on any
  managed cluster: hostPath is node-local, and GKE Autopilot rejects it.

  Setting it on a release that already holds data is a **data move** — copy the
  directory across with the workload stopped, or the database will come up
  empty.
</Callout>

Nothing in the chart deletes a database. The StatefulSet sets
`persistentVolumeClaimRetentionPolicy: Retain`, so neither `helm uninstall` nor
scaling to zero removes the claim, and the static volume carries
`helm.sh/resource-policy: keep` so an uninstall leaves it for the next install to
adopt. Destroying storage is the infrastructure layer's job.

### Agentic runner

Configure the image the orchestrator deploys for an integration whose deployment
asked for `runner: agentic` — the one carrying a shell, `curl`, `jq`, the
standalone `octo` CLI, `dolphin` and a scratch workspace. Leave these at their
defaults unless you are turning the runner off or sizing its pod. The
[platform agent](/platform/agent) requires it; see
[octo-agenticrunner](/deploy/docker-images#octo-agenticrunner) for what is in it.

| Key | Default | Purpose |
|---|---|---|
| `agenticrunner.repository` | `octo-agenticrunner-paas` | The image. Follows the same registry/tag/digest layering as every other component. |
| `agenticrunner.workspaceSize` | `100Mi` | Cap on the `/workspace` `emptyDir`. A cap, not an allocation — the volume costs nothing until it is written to. |
| `agenticrunner.resources` | `{}` | Requests and limits for the container, as an ordinary resources block. Passed to the orchestrator as JSON, because integration pods are created by it at deploy time rather than rendered by this chart — the same reason `runtime.imagePullSecrets` needs saying separately. |

**To turn the runner off**, clear `agenticrunner.repository`. That removes it
rather than degrading it: the orchestrator then refuses an agentic deploy naming
this value instead of serving the distroless image and leaving every command in
the flow to fail with *not found*, and installing the agent is blocked up front
with the reason shown rather than producing a crash-looping pod.

Two things to weigh before you grant it.

**Treat the pod as the boundary.** This runner is privileged, not merely bigger:
a pod holding a shell and a runtime it can point at a definition it wrote a
moment ago is a general execution environment, so no allow list inside the flow
contains it. Assume everything that pod holds — including secrets bound to its
environment — and everything it can reach on the network is reachable by anything
it runs, and grant it per deployment on that basis.

**Set `resources` where a pod's appetite matters.** No integration pod carries
requests or limits by default, and this is the one workload whose purpose is
running other programs. Set them on GKE Autopilot, which requires them, and
anywhere this pod's CPU should not become the node's problem.

### Dev runs

The editor's **Run** button, executed as a pod the orchestrator creates rather than
as a child process of whichever platform replica answered the request. That is the
whole point: the platform app runs several replicas with no session affinity, so a
run living in one replica's memory is invisible to every other one — status reads
report "not running", log streams attach to nothing, and a Stop lands on the wrong
pod. On by default, since this is the chart that runs several replicas; turn it off
for a single-replica install, which has no such problem. See
[Dev runs](/platform/dev-runs) for what the feature does.

| Key | Default | Purpose |
|---|---|---|
| `orchestrator.devRuns.enabled` | `true` | Turn the feature off, or leave it on. Renders the two images, the sidecar port, the idle timeout and the key Secret into the orchestrator's environment; without them the orchestrator reports dev runs unavailable and the editor's Run says so. |
| `orchestrator.devRuns.hashSecret` | `""` | **Required.** HMAC key deriving each run's identity and its public hostname from (user, integration). |
| `orchestrator.devRuns.existingSecret` / `.existingSecretKey` | `""` / `dev-run-hash-secret` | That key from a Secret you already hold. The requirement is on the pair, not on `hashSecret` alone. |
| `orchestrator.devRuns.idleTimeout` | `60m` | How long a run survives untouched before the orchestrator reaps it. The only bound on how many pods an editing session leaves behind — there is no per-user cap. |
| `orchestrator.devRuns.sidecarPort` | `8099` | Port the run's sidecar serves its reload/status API on, inside the pod. Never reached from outside it. |

Two things worth knowing before turning it on.

**The key must never change.** A run's public hostname is derived from it, so
rotating it re-labels every exposed dev run — and a webhook registered with Stripe
or GitHub against the old hostname silently stops being delivered, with no error
anywhere. That is why the chart requires the value instead of generating one: a
generated key would be regenerated by any render that cannot read the cluster
(`helm template`, `--dry-run`, a GitOps pipeline). Generate it once and hold it
wherever you hold `kv.encryptionKey`.

Holding it in a Secret rather than a values file is the better answer for both —
and for every other credential the chart takes. `existingSecret` is how, and it
is the same shape everywhere:

```yaml
postgres:
  auth:
    existingSecret: octo-postgres  # key: postgres-password
kv:
  existingSecret: octo-kv          # key: kv-encryption-key
auth:
  existingSecret: octo-auth        # keys: oidc-client-secret, auth-secret
embeddings:
  existingSecret: octo-embeddings  # key: apiKey
orchestrator:
  devRuns:
    existingSecret: octo-devruns   # key: dev-run-hash-secret
```

The chart then creates none of those Secrets and never sees any of the values, so
no key material lands in the release history — only names and keys, which are
references and not credentials. The same goes for whatever wrote the values, which
for a GitOps repository or a deployment record in an operations panel outlives the
release by a long way.

<Callout type="warn">
  **`--set-file` and `set_sensitive` do not help.** They change how a value is
  supplied and how it is printed, not where it ends up: Helm writes every value it
  is given into the release Secret in the cluster, and keeps it for every retained
  revision. A reference is the only form that does not.
</Callout>

Clear the inline value when you switch. Setting both is refused rather than
resolved by precedence, and the reason is worth stating: suppressing the chart's
Secret does not unsay the value, because Helm keeps everything it is given in the
release history whether a template renders it or not. Leaving `encryptionKey`,
`hashSecret`, `apiKey` or the two `auth` values in place beside an
`existingSecret` would keep exactly the copy the switch was made to avoid, while
reading as though it had been moved.

Migrating an installation that already has one inline is worth being clear-eyed
about, too: revisions written before the change still hold what they were given,
and `helm history` keeps them. If that matters, the moment to fix it is before
anything has been encrypted or deployed — while these keys can still be replaced,
which is not true afterwards.

**A dev-run hostname is stable but not private.** It is an unguessable hash, not an
access control. With `orchestrator.clusterIssuer` set, each one also gets a
per-host certificate and therefore an entry in public CT logs — so prefer
`wildcardTLS` (one `*.{baseDomain}` certificate) when dev runs are on. Without
`orchestrator.baseDomain` a run still works; it simply publishes no external
address, and a networked integration is reachable only in-cluster.

### Data retention

A CronJob that asks the aggregator, once a night, to delete stored logs and traces older than the site's retention policy.

**Two switches, answering different questions.** These values decide whether the job exists and when it runs. *How long to keep things* is not here — it is a policy in the database, edited in the admin section, because it is an operational decision rather than a deployment one. See [Data retention](/platform/logs-api-reference#data-retention).

| Key | Default | Purpose |
|---|---|---|
| `retention.enabled` | `true` | Install the CronJob. Safe as a default because the policy defaults to keeping everything: a fresh install sweeps nightly and deletes nothing until somebody sets a window. Turning it off removes the schedule, not the capability — the endpoint stays served, so an on-demand sweep still works. |
| `retention.schedule` | `0 3 * * *` | When it runs, in the cluster's timezone. The small hours on purpose: the first sweep after a policy is set can be the whole of both tables, and it competes with ingest while it runs. |
| `retention.timeoutSeconds` | `900` | How long `curl` waits. It matches the aggregator's own limit on a sweep, so neither side abandons the other — a client that gave up first would drop a purge that was making progress, every night, and never converge. |
| `retention.concurrencyPolicy` | `Forbid` | Skip a run while the previous one is still going, rather than stacking sweeps that would only refuse each other with a `409`. |
| `retention.backoffLimit` | `2` | Retries within one scheduled run. Low on purpose: each batch commits on its own, so a failed sweep is less deleted rather than something inconsistent, and tomorrow's run picks up where it stopped. |
| `retention.image.*` | `curlimages/curl` | The job is one HTTP POST and the octo images are distroless — no shell, no client. Third-party, so it takes its registry from `retention.image.registry` alone (empty means Docker Hub) rather than from the shared `image.registry`, exactly as `postgres` and `nats` do. |

## Redis

Redis holds state that has to be shared between replicas of a component rather
than kept in one process. Today that is one thing: the telemetry aggregator folds
the run of trace records a streaming block emits — one `block.pre-invoke` and one
`block.post-invoke` per streamed token — into a single row. The aggregator's
consumers are a NATS queue group, so a single trace's records are already spread
across whichever replicas are running, and a fold held in one process would
quietly stop working the moment `logs.replicas` went above 1.

**It is not optional the way NATS is.** `nats.enabled=false` degrades a feature —
live event streams fall back to polling. Turning Redis off does not degrade
anything: the aggregator refuses to start without one. So an install with neither
the bundled server nor `externalRedis.url` **fails while rendering**, with a
message naming both values. That is deliberate. The alternative is a component
that comes up healthy and silently stops folding, which is invisible until the
`traces` table is large.

Nothing here is persisted, on either side: no volume, and the server runs with
`--save ""` and `--appendonly no`. What lives in it is regenerated within seconds
of being lost, and losing it costs at most the trace records in the folds that
were open — the same at-most-once contract the rest of the trace pipeline ships
with.

To use a managed Redis instead:

```yaml
redis:
  enabled: false
externalRedis:
  url: redis://cache.internal:6379
```

The whole connection is that one string. **If it contains a password, put it in a
Secret instead** — `externalRedis.url` is rendered into the workload as a literal
environment value, and a rendered Deployment is readable by anyone who can read
workloads, which is a wider audience than anyone who can read Secrets:

```bash
kubectl create secret generic octo-redis \
  --from-literal=redis-url='rediss://default:pw@cache.example:6380'
```

```yaml
redis:
  enabled: false
externalRedis:
  existingSecret: octo-redis   # wins over `url` when both are set
  existingSecretKey: redis-url # the default
```

The chart will not create that Secret for you, for the same reason it keeps the
database's password out of its DSN: a credential you own should not have to pass
through a values file to reach the cluster.

Whether the cluster's Redis is actually reachable is on the
[Platform services](/platform/admin-settings) page, alongside Postgres, NATS and
the Kubernetes API.

### What the chart does not create

Four things a production chart often ships are deliberately absent. They are
listed here so their absence reads as a decision rather than an oversight, and
because each has a workable answer in the meantime:

| Not shipped | Why | If you need it |
|---|---|---|
| **PodDisruptionBudget** | A PDB on a single-replica Deployment either permits the eviction it was meant to prevent or blocks node drains outright. It becomes meaningful once you raise `replicas`, and meaningful differently per component. | Apply your own alongside the release; the components carry standard `app.kubernetes.io/component` labels to select on. |
| **HorizontalPodAutoscaler** | The editor and orchestrator are not the throughput-bound part of this system — integration pods are, and those are created by the orchestrator, not by this chart. An HPA on the chart's own workloads would scale the wrong thing. | Apply your own; `platform` and `logs` scale horizontally without coordination, the orchestrator is safe to scale but gains little. |
| **NetworkPolicy** | Correct policies depend on what else runs in the namespace and which CNI enforces them, and a policy that is silently unenforced is worse than none — it reads as protection that is not there. | Write them against the component labels. The orchestrator needs the API server; every service needs Postgres and NATS. |
| **Topology spread / anti-affinity by default** | The knobs exist (`defaults.topologySpreadConstraints`, `defaults.affinity`) and the GKE Standard profile uses them; defaulting them would make single-node clusters unschedulable. | Set them per environment — see `values-gke-standard.yaml`. |

## Image and chart compatibility

The chart and the images are released together and are tested together. A chart
at version X expects the images of release X, which is what it installs by
default via the `appVersion` fallback.

This matters because **the images run as non-root**, and the chart's cloud
profiles pin the matching UIDs:

| Image | Runs as |
|---|---|
| `octo-platform-paas` | `1000` (`node`) |
| `octo-orchestrator-paas`, `octo-logs-paas`, `octo-runtime-paas` | `65532` (distroless nonroot) |
| `octo-schema-paas`, `postgres` | `70` (`postgres`) |
| `nats` | any UID |

Pinning `image.tag` to an older release while using a newer chart is not a
combination that gets tested, and the security contexts in the profiles are the
most likely thing to break. If you must mix versions, relax
`defaults.securityContext` accordingly.

## Cluster prerequisites

The chart deploys workloads, not cluster infrastructure. Depending on the values
you choose, the cluster must already provide:

- an **ingress controller** matching `ingress.className` — none is installed here
- **cert-manager** and a ClusterIssuer, for `tls.mode: cert-manager` (and for
  `wildcardTLS`, which needs a DNS-01 issuer)
- a **StorageClass** for the Postgres PVC, unless `postgres.storage.hostPath` is
  set or `postgres.enabled` is `false`

## Upgrade

<DynamicCodeBlock lang="bash" code={`helm upgrade octo oci://ghcr.io/juancavallotti/charts/octo \\
  --version ${OCTO_VERSION} --namespace octo --reuse-values`} />

Because `image.tag` follows `appVersion`, a chart-version bump moves the images
with it — there is no second tag to remember. What happens:

- changed image references rewrite the pod templates, so the platform,
  orchestrator and logs Deployments roll automatically
- the schema hook Job re-runs and applies `sql/schema.sql`; the schema is
  idempotent (`IF NOT EXISTS` / `ON CONFLICT`), so this is safe every time
- Postgres and its PVC are untouched — your data survives the upgrade
- integrations already deployed keep running on the runtime image they were
  deployed with; redeploy them from the editor to pick up a new `octo-runtime`

<Callout type="warn">
  In the GCP reference deployment, Terraform owns the Helm release — do not run
  `helm upgrade` against it by hand. Apply the `release` root (or
  `task deploy TAG=…`) instead.
</Callout>

## Validating changes

a template change that breaks a target you cannot reach locally still fails on
the pull request.
